fraud-detection-xgboost — system architecture

Two training lanes, one shared feature store, two serving endpoints.

Ingest once, split chronologically, then fork: a baseline model trained on raw features, and a second model augmented with Feast-served IP-reuse features — kept as two separately registered MLflow models so the comparison between them stays honest and reproducible, not two branches of the same script quietly diverging.

01What this shows that the README's prose can't

The diagram exists to make one structural fact impossible to miss: this isn't one pipeline with a feature-store flag — it's two complete, parallel lanes from the same split data, converging only at MLflow, and diverging again at serving. The Feast lane itself also splits in two: the point-in-time join that feeds train_with_feast.py and the materialized online store that feeds /predict_feast are different mechanisms answering different questions — "what did this IP look like back then" versus "what does this IP look like right now."

03The finding this architecture surfaced

Both registered models scored identically (PR-AUC 0.6758, ROC-AUC 0.8256). Verified cause: the dominant IP-reuse burst landed entirely inside the test split, so the Feast lane's three extra columns were constant zero throughout every training run — the model correctly learned to ignore them. The two-lane structure above is exactly what made this comparison possible to run and diagnose in the first place, rather than guessing whether a feature "helped."
