Redis, Kafka, RabbitMQ and friends: what each one is and when to use it

These tools all "move messages", which makes them sound interchangeable. They aren't. Each is built around one of a few different models, and the model decides what it's good at. Learn the models first, then the tools become easy to place.

2. Is Kafka a queue?

No: Kafka is a log. You can use it like a queue, but it behaves differently, and the difference shows up as soon as jobs are slow or uneven. The key difference is what happens after a message is read:

  • Queue (RabbitMQ, SQS): a worker takes a message, finishes it, and acks it. The message is deleted. It's like a to-do list where you cross items off.
  • Kafka: a reader reads a message and the message stays. Kafka only remembers how far each reader has got ("billing has read up to #42"). It's like a book where each reader keeps their own bookmark.

Example: 3 jobs, where job A takes 1 hour and B and C take 1 second each

QueueKafka (A, B, C in the same partition)
Who works on whatWorker 1 takes A. Workers 2 and 3 take B and C at once.One consumer reads that partition, in order.
When B and C finishAfter about 1 secondAfter about 1 hour, because they wait behind A
If A's worker crashesOnly A is retriedThe bookmark hasn't moved, so A, B and C are all read again

Why people still call it a queue

For fast, uniform messages (milliseconds each, like click events or log lines), a log works perfectly well as a queue, and Kafka does that at huge scale. Its real strengths are things a queue can't do: keeping history, replaying it, and letting many different services each read the same messages at their own pace.

Kafka 4.x is adding share groups (KIP-932, "queues for Kafka") with per-message acks and queue-style consumers, which narrows the gap. It's new and not what most Kafka setups use today, so check how mature it is before relying on it.

Rule of thumb: "Someone please do this job" → a queue (RabbitMQ, SQS, Postgres, Redis). "This happened, anyone who cares can read it, now or later" → Kafka.

3. Vocabulary you need

TermMeaningWhy it matters
AckThe consumer tells the broker "I've finished this message".No ack before a timeout means the broker assumes you crashed and redelivers.
At-most-onceDelivered zero or one times. Fire and forget.Fine for metrics or live presence. Never for payments or jobs.
At-least-onceDelivered one or more times. Retried until acked.The normal choice. Consumers must tolerate duplicates (be idempotent).
Exactly-onceThe effect happens once.Only within a closed system (e.g. Kafka transactions, SQS FIFO deduplication window). End to end you get it with at-least-once + idempotent consumers.
Visibility timeout / leaseHow long a received message is hidden from other consumers.Must be longer than your processing time, or be extended while you work.
Consumer groupA set of consumers sharing the work of one subscription.In Kafka, parallelism is limited to the number of partitions.
PartitionA slice of a topic. Ordering is guaranteed only within a partition.Pick a partition key (e.g. user ID) for per-key ordering.
OffsetA consumer's position in a log.Rewind it to replay history.
Dead-letter queue (DLQ)Where messages go after failing too many times.Stops one bad message ("poison pill") from blocking or looping forever.
BackpressureSlowing producers or buffering when consumers can't keep up.The main reason to put a broker between services at all.
PrefetchHow many unacked messages a consumer may hold.Set it to 1 for long jobs, so one worker doesn't hoard work.

4. The tools, one by one

Self-hosted / open source (run anywhere)

Redis

in-memoryqueue + pub/sub + log

An in-memory data store that has three messaging features: Lists (simple queue), Pub/Sub (fire-and-forget fan-out), and Streams (a log with consumer groups and acks).

Great at
Very low latency. Simple. You probably already run it for caching. Backs Celery, RQ, arq and Sidekiq.
Weak at
Durability (memory first, async replication: a crash or failover can lose recent messages). Data must fit in RAM. Pub/Sub drops messages for offline subscribers.
Use when
Background jobs for a web app, rate limiting, live notifications, small-to-medium task queues where a rare lost message can be recovered from a database.
Avoid when
It would be the only record of something that must never be lost (orders, payments).

RabbitMQ

brokerqueue + routingAMQP

The classic message broker. Producers publish to exchanges, which route to queues by rules (direct, topic pattern, fanout, headers). Consumers get messages pushed and ack each one.

Great at
Task queues, flexible routing, priorities, per-message ack/retry, dead-letter exchanges, low latency. Quorum queues replicate for durability.
Weak at
Replay (acked messages are gone, though Streams add a log). Very large backlogs. Throughput is high, but lower than Kafka at the extreme end.
Use when
Background jobs, microservice commands ("resize this image"), routing work by type or priority, RPC-style request/reply.
Avoid when
You need an event history to replay, or millions of events per second.

Apache Kafka

distributed logevent streaming

A replicated, partitioned, append-only log. Messages are retained by time or size. Consumers track their own offsets, so many independent groups can read the same data, and anyone can replay it.

Great at
Very high throughput, ordering per key, replay, fan-out to many consumer groups, event sourcing, change-data-capture (Debezium), stream processing (Kafka Streams, Flink). Huge ecosystem (Connect, Schema Registry).
Weak at
Job-queue behaviour: no per-message ack (share groups in Kafka 4.x are changing this), a slow message blocks its partition, and parallelism is capped by partition count. Heavy to operate yourself.
Use when
Activity and clickstreams, logs and metrics pipelines, CDC, the "central nervous system" connecting many services, anything you'll want to replay.
Avoid when
You just need a background job queue, or your volume is small. It's a lot of infrastructure for little benefit.

Redpanda

Kafka-compatible log

A reimplementation of Kafka in C++ that speaks the Kafka protocol. A single binary with no JVM and no separate coordination service.

Great at
Kafka semantics with simpler operations and lower latency. Kafka client libraries work unchanged.
Weak at
Smaller community than Kafka. Source-available licence; check the terms.
Use when
You want Kafka's model without running Kafka.

NATS (+ JetStream)

lightweightpub/sub + queue + log

Core NATS is very fast at-most-once pub/sub and request/reply. JetStream adds persistence: streams, durable consumers with acks, redelivery, and a work-queue mode.

Great at
Tiny single binary, very low latency, request/reply between services, edge and IoT, multi-cloud clustering. Consumers can signal "still working" on long jobs.
Weak at
Smaller ecosystem than Kafka or RabbitMQ. Fewer managed offerings.
Use when
Service-to-service messaging, edge or IoT, or one simple tool that covers pub/sub, queues and streams.

Apache Pulsar

log + queuemulti-tenant

Stateless brokers in front of a separate storage layer (BookKeeper). Supports both streaming and queue-style "shared" subscriptions with per-message acks.

Great at
Built-in multi-tenancy (tenants and namespaces), geo-replication, tiered storage to object stores, queue and stream in one system.
Weak at
The most moving parts of any tool here. Smaller community than Kafka.
Use when
A large platform team serving many internal tenants, with geo-replication needs.

Postgres as a queue

databasequeue

A jobs table claimed with SELECT ... FOR UPDATE SKIP LOCKED, optionally woken by LISTEN/NOTIFY. Libraries: Procrastinate, pgmq, Oban (Elixir), River (Go), Solid Queue (Rails).

Great at
No extra infrastructure. Enqueueing is in the same transaction as your data, so a job and its data can't get out of sync. Easy to inspect with SQL.
Weak at
Very high throughput. Fan-out. It adds load to your main database.
Use when
Small to medium job volumes, or long-running jobs where correctness matters more than speed. This is often the right first choice.

Postgres as a queue

Temporal / Hatchet / Restate / DBOS

workflow enginedurable execution

Not brokers. You write a workflow as ordinary code, and the engine records each step so it can resume after crashes, with retries, timers, and waits lasting days.

Great at
Long multi-step processes: orders, onboarding, AI agent runs, sagas across services, human approvals.
Weak at
A new programming model to learn (Temporal workflows must be deterministic). Not meant for high-volume event streaming.
Use when
You notice you're hand-building retries, state machines and timeouts on top of a queue.

6. When to use what

Answer these in order and stop at the first "yes".

#QuestionIf yes
1Is it a multi-step process that must survive crashes, wait for people or timers, or run for hours?Workflow engine (Temporal, Hatchet). Or a Postgres queue with checkpoints if it's simple.
2Do several different systems need the same events, or will you want to replay history?Log: Kafka / Redpanda (or Kinesis, Event Hubs, Pub/Sub on that cloud).
3Is it "do this job once, by any worker"?Queue. Already have Postgres and modest volume: Postgres queue. Need routing, priorities or high rates: RabbitMQ. All-in on one cloud: SQS / Service Bus / Pub/Sub. Already running Redis and a lost job is recoverable: Redis.
4Is it a live notification where missing one is fine (presence, "new message" ping, cache invalidation)?Lightweight pub/sub: Redis Pub/Sub or core NATS.
5Is it service-to-service request/reply with low latency?Plain HTTP or gRPC first. NATS if you want a messaging layer for it.

7. Common combinations

  • Postgres + transactional outbox → Kafka. Write business data and an event in one transaction. A relay (or Debezium) publishes the event, so the database and the stream never disagree.
  • SNS → several SQS queues (AWS) or Kafka topic → several consumer groups. Each downstream service gets its own queue or position and fails independently.
  • Queue for jobs, Kafka for events. RabbitMQ, SQS or Postgres dispatches the work; Kafka records what happened, for analytics, audit and other services.
  • Redis next to a durable store. Redis for speed (rate limits, live updates, caches). Postgres or Kafka holds the truth.
  • Workflow engine with a queue at the edge. A queue absorbs incoming bursts, and the workflow engine runs each long process.

8. Common mistakes

MistakeWhat goes wrongInstead
Using Kafka as a job queue for slow jobsA slow message blocks its partition. The consumer is removed from the group after max.poll.interval.ms, which causes duplicates and rebalance storms.Use a queue for jobs, Kafka for events.
Using Redis Pub/Sub for something importantSubscribers that are offline or reconnecting silently miss messages.Redis Streams, or a real queue.
Making Redis the only copy of critical jobsA crash or failover loses recently accepted messages.Keep the truth in a database, and re-enqueue from it.
Processing time longer than the visibility timeout or ack deadlineThe broker redelivers mid-job and two workers do the same work.Extend the timeout while working (heartbeat), or ack early and track the job with a lease.
Assuming "exactly-once delivery"Duplicates still happen at the edges (retries, redeliveries).At-least-once delivery + idempotent consumers (deduplicate by message or job ID).
Writing to the DB and the broker separatelyA crash between the two leaves them inconsistent.Transactional outbox.
No dead-letter queueOne poison message retries forever or blocks the queue.Cap attempts and move failures to a DLQ you monitor.
Adding Kafka on day one "for scale"Lots of operations and complexity for a few hundred messages a minute.Start with Postgres or Redis. Move when there's a measured need.

One-line summary: queues hand out work (RabbitMQ, SQS, Postgres, Redis), logs keep a replayable history (Kafka, Kinesis, Pulsar), pub/sub broadcasts (SNS, Redis Pub/Sub, NATS), and workflow engines run long processes to completion (Temporal, Hatchet). Pick the model first, then the tool that fits your cloud and your team's capacity to operate it.
