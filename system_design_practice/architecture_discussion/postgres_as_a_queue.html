Postgres as a queue

Postgres has no built-in "queue feature" to switch on. A Postgres queue is a pattern built from ordinary features every Postgres 9.5+ already has: a table, row locks, SKIP LOCKED, transactions, and optionally LISTEN/NOTIFY. This page shows how it works, step by step, and when to use it.

1. The building blocks

FeatureWhat it isRole in the queue
A normal tableRows and columnsHolds the jobs, one row per job
Row locks (SELECT ... FOR UPDATE)Locks the selected rows until the transaction endsA worker locks the job it takes, so no one else can change it
SKIP LOCKEDTells the query to ignore rows another transaction has locked, rather than wait for themThis is what makes it a queue. Many workers can grab jobs at once without colliding or blocking.
TransactionsAll-or-nothing groups of statementsCreating a job can be atomic with your business data. A crash mid-transaction releases the job.
Partial indexAn index over only the rows matching a conditionKeeps "find the next queued job" fast even with millions of finished rows
LISTEN / NOTIFYLightweight pub/sub built into PostgresOptional: wake workers the moment a job arrives instead of polling

3. Building it step by step

Step 1: create the jobs table

Just SQL. No extension, nothing to enable.

CREATE TABLE jobs (
  id            bigserial PRIMARY KEY,
  payload       jsonb NOT NULL,
  status        text NOT NULL DEFAULT 'queued',   -- queued | running | done | failed
  attempts      int  NOT NULL DEFAULT 0,
  max_attempts  int  NOT NULL DEFAULT 3,
  locked_by     text,
  locked_until  timestamptz,                      -- the lease
  last_error    text,
  run_after     timestamptz NOT NULL DEFAULT now(),  -- for delayed jobs and retry backoff
  created_at    timestamptz NOT NULL DEFAULT now()
);

-- Only covers rows still waiting, so it stays small and fast
CREATE INDEX jobs_ready ON jobs (run_after) WHERE status = 'queued';

Step 2: enqueue a job

A normal insert. Because it's an ordinary write, it can share a transaction with your business data:

BEGIN;
  INSERT INTO runs (id, tenant_id, ...) VALUES ('r_123', 't_1', ...);
  INSERT INTO jobs (payload) VALUES ('{"run_id": "r_123"}');
COMMIT;   -- both rows exist, or neither does

This is the biggest advantage over a separate broker. With RabbitMQ, Kafka or SQS, saving data and enqueueing are two writes to two systems, which needs a "transactional outbox" to stay consistent. Here it's one transaction.

Step 3: claim a job (the core query)

UPDATE jobs
SET status       = 'running',
    attempts     = attempts + 1,
    locked_by    = 'worker-7',
    locked_until = now() + interval '60 seconds'
WHERE id = (
  SELECT id FROM jobs
  WHERE status = 'queued' AND run_after <= now()
  ORDER BY run_after
  FOR UPDATE SKIP LOCKED      -- lock one row, skip rows other workers hold
  LIMIT 1
)
RETURNING *;

Reading it inside out: the subquery finds the oldest ready job that no one else has locked and locks it. The outer UPDATE marks it as taken by this worker. RETURNING * hands the job back. If no row comes back, the queue is empty.

Step 4: finish the job

-- success
UPDATE jobs SET status = 'done', locked_until = NULL
WHERE id = $1 AND locked_by = 'worker-7';   -- only if we still own it

-- failure: retry later with backoff, or give up
UPDATE jobs
SET status    = CASE WHEN attempts >= max_attempts THEN 'failed' ELSE 'queued' END,
    run_after = now() + (interval '30 seconds' * power(2, attempts)),
    last_error = $2, locked_by = NULL, locked_until = NULL
WHERE id = $1 AND locked_by = 'worker-7';

The locked_by check matters: if this worker was presumed dead and the job was re-claimed by someone else, the stale worker's update affects zero rows instead of overwriting the new owner's work.

Step 5: heartbeat (long jobs only)

While working, extend the lease every ~20 seconds so nobody thinks the worker died:

UPDATE jobs SET locked_until = now() + interval '60 seconds'
WHERE id = $1 AND locked_by = 'worker-7';

4. Two ways to hold a job

StyleHowCrash recoveryGood for
Lock for the whole job BEGIN → claim with FOR UPDATE SKIP LOCKED (no status change needed) → do the work → mark done → COMMIT Automatic: if the worker dies, its connection drops, the transaction rolls back, and the row is unlocked. Short jobs (seconds)
Claim, commit, lease (step 3 above) Claim and COMMIT straight away. Track liveness with locked_until and heartbeats. You handle it: expired leases get picked up again (next section). Long jobs (minutes to hours), like AI agent runs

Why not hold a transaction open for an hour? Each open transaction pins a database connection for its whole duration, so 50 running jobs need 50 connections. Worse, Postgres can't clean up old row versions (vacuum) that are newer than the oldest open transaction, so tables across the whole database bloat and slow down.

5. Crash recovery and retries

With the lease style, a crashed worker leaves its job in running with a locked_until in the past. Two ways to recover it:

Option A: let the claim query pick it up

WHERE (status = 'queued' AND run_after <= now())
   OR (status = 'running' AND locked_until < now())   -- lease expired: worker presumed dead

Option B: a periodic reaper

-- run every minute (cron, pg_cron, or a loop in one worker)
UPDATE jobs
SET status = CASE WHEN attempts >= max_attempts THEN 'failed' ELSE 'queued' END,
    locked_by = NULL, locked_until = NULL,
    last_error = 'lease expired'
WHERE status = 'running' AND locked_until < now();

Either way, the job may run a second time. Make jobs idempotent (safe to repeat), or checkpoint progress so a retry continues where the last attempt stopped.

Rows that end in failed are your dead-letter queue. Unlike a broker's DLQ, you can inspect, filter and re-queue them with plain SQL:

UPDATE jobs SET status = 'queued', attempts = 0, run_after = now()
WHERE status = 'failed' AND last_error LIKE '%rate limit%';

6. How 50 pods avoid processing the same job

Picture 50 worker pods, all running the claim query against the same jobs table, many of them at the same instant. Why doesn't a job get picked up by two or three of them?

The guarantee: a queued job can be taken by exactly one claim query, however many pods are polling. Duplicate processing can only come from two later situations: a lease that expires while its pod is still working, or a pod that crashes after doing the work but before marking it done. Both are handled with a fencing token and idempotent work (covered below).

Tested: 50 workers, 5,000 jobs, four ways of claiming

Each strategy was run with 50 concurrent workers (one database connection each, like 50 pods) against a fresh table of 5,000 jobs. Every time a worker claimed a job it wrote a row to a processed log. Any job that appears in the log more than once was processed more than once.

Claim strategyTimes jobs were processedJobs processed more than onceWorst case for one jobWasted attemptsPods that got workTime

Laptop timings with near-instant "work". The pattern is what matters: the naive version processed one job 24 times. The optimistic version is correct but burns 16 failed attempts per job. Plain FOR UPDATE is correct but makes workers queue behind each other's locks, so only half of them ever got a job. SKIP LOCKED is correct, uses every pod, and is fastest.

Layer 1: claiming must be one atomic step

The naive version splits "find a job" and "take the job" into two statements. Between them, other pods see the same job as free:

TimePod APod B
t1SELECT id ... WHERE status='queued' LIMIT 1 → job 7
t2SELECT id ... WHERE status='queued' LIMIT 1 → job 7 (still queued)
t3UPDATE jobs SET status='running' WHERE id=7
t4UPDATE jobs SET status='running' WHERE id=7 (succeeds too)
t5runs job 7runs job 7

With 50 pods all reading "the oldest queued job" at once, they mostly read the same row, which is why the test saw up to 24 copies of one job. The fix is to find and take the job in one statement that locks the row.

Layer 2: the row lock, and SKIP LOCKED

In SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1, each pod scans the queued jobs in order and tries to lock each row:

  • Locking a row is atomic inside Postgres. If 50 pods reach job 7 in the same microsecond, exactly one gets the lock.
  • The other 49 see the row is locked. With SKIP LOCKED they move straight on to job 8, 9, 10 and so on, and each takes the first row it can lock. 50 pods end up with 50 different jobs.
  • The outer UPDATE sets status = 'running' in the same statement, and with autocommit the change commits as soon as the statement finishes. The lock is held only for that instant, not for the whole job.

Without SKIP LOCKED, the 49 losing pods wait for the winner's lock to be released. That's still correct, but they form a queue behind one row, which is the "only 25 pods got work" result above.

Layer 3: Postgres re-checks the row after locking it

There's one subtler race. Pod B's query may have started reading just before pod A committed. B's snapshot still shows job 7 as queued, and by the time B reaches the row, A's lock is already gone, so SKIP LOCKED doesn't apply. Why doesn't B take job 7?

TimePod APod B
t1locks job 7, sets status='running'query starts; its snapshot shows job 7 as queued
t2commits (lock released)
t3reaches job 7, locks it (no longer locked), then re-reads the newest version: status='running'
t4the WHERE status = 'queued' check now fails, so B drops job 7 and continues to job 8

Under the default READ COMMITTED isolation level, when FOR UPDATE (or an UPDATE) locks a row that changed after the query's snapshot, Postgres re-evaluates the WHERE clause against the newest committed version of that row. This is why the claim query must filter on status and must change status in the same statement: the status change is what the re-check sees.

Layer 4: one clock for all pods

Lease checks use now(), which is the database server's clock. Fifty pods with slightly different system clocks can't disagree about whether a lease has expired, because none of them use their own clock for it. Don't compute locked_until in application code.

Where duplicates can still happen

The claim itself never hands one job to two pods. But a job can still be executed twice in these cases:

SituationWhat happensDefence
Lease expires while the pod is still alive (long GC pause, network blip, missed heartbeats, slow step)The job looks abandoned, so another pod reclaims it. Now two pods run it at once.Heartbeats well inside the lease (e.g. every 20 s for a 60 s lease), plus a fencing token so the stale pod's writes are rejected
Pod crashes after the work, before marking doneThe lease expires and the job runs again.Idempotent work, or do the work's database writes and "mark done" in one transaction
The "done" update is lost (connection drops at commit)The pod can't tell if it committed, so the job may be retried.Same as above: idempotency
The same job is enqueued twice (client retries a submit)Two different rows, both valid, so both run.A unique idempotency key: UNIQUE (tenant_id, idempotency_key) plus ON CONFLICT DO NOTHING

Fencing token: rejecting a stale pod's writes

Use the attempts counter as a token. The claim increments it and returns it. Every later write for that job includes AND attempts = <my token>, so only the newest owner's writes take effect:

-- claim returns (id, attempts); keep attempts as the fencing token
UPDATE jobs SET status = 'done', result = $3
WHERE id = $1 AND attempts = $2;     -- 0 rows = someone newer owns this job: stop, don't overwrite

Tested with a 2-second lease (postgres_queue_lab/lease_test.py):

pod-A claims job 1 attempt 1
pod-B tries immediately: None (nothing: A holds the lease)
pod-A stalls 3s with no heartbeat (GC pause / network blip)...
pod-B reclaims job 1 attempt 2  <- job now running on TWO pods
pod-B finishes, fenced update rows: 1
pod-A wakes, fenced update rows: 0 (rejected: stale attempt)
final row: ('done', 2, 'pod-B', 'B')

Fencing protects the jobs table. It can't undo what pod A already did outside it, such as sending an email or calling an API. That's what idempotency is for.

Making the work itself idempotent

Kind of side effectPattern
Writes to the same Postgres databaseDo the writes and UPDATE jobs SET status='done' ... AND attempts = $token in one transaction. If the fenced update hits 0 rows, roll back. This gives an exactly-once effect.
Rows the job producesA unique constraint on the output (e.g. UNIQUE (job_id)) plus INSERT ... ON CONFLICT DO NOTHING
External APIs (payments, email, tickets)Send an idempotency key derived from the job, e.g. job_id + step number. Most payment and messaging APIs support this.
Long multi-step work (agent runs)Checkpoint after each step, so a retry resumes rather than repeating finished steps

Checklist for running 50 pods

  • Claim in one statement with FOR UPDATE SKIP LOCKED, filtering on status and changing status in the same statement.
  • Keep the claim in a shape that runs the locking subquery once: WHERE id = (SELECT ... LIMIT 1) as on this page, or a CTE. EXPLAIN should show it as an InitPlan. Rewrites such as IN (...) or joins give the planner more freedom in how it runs the subquery, so check their plans carefully.
  • Lease and heartbeat: heartbeat at most a third of the lease length. Use now() from the database, not the pod's clock.
  • Fence every write after the claim with AND attempts = $token.
  • Make side effects idempotent, and put a unique idempotency key on enqueue.
  • Connections: 50 pods × pool size must stay under max_connections. Use PgBouncer in transaction mode if needed: the claim is a single statement, so it works there. LISTEN does not work through transaction pooling, so give listeners a direct or session-pooled connection.
  • Batch claims (LIMIT 5) if pods process many short jobs, to cut round trips.

7. Waking workers: polling vs LISTEN/NOTIFY

ApproachHowTrade-off
PollingRun the claim query; if empty, sleep 1 second and try againDead simple and robust. Adds up to 1 second of delay and a small constant query load. Cheaper than it sounds: see section 8.
LISTEN/NOTIFYThe producer runs NOTIFY jobs_channel; idle workers LISTEN and wake immediatelyNear-instant pickup. Notifications aren't stored: a worker that's disconnected misses them. So always keep a slow poll as a fallback.
-- producer: in the same transaction as the insert (delivered on COMMIT)
INSERT INTO jobs (payload) VALUES ('{"run_id": "r_123"}');
NOTIFY jobs_channel;

-- or automatically with a trigger
CREATE FUNCTION notify_new_job() RETURNS trigger AS $$
BEGIN
  PERFORM pg_notify('jobs_channel', NEW.id::text);
  RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER jobs_notify AFTER INSERT ON jobs
FOR EACH ROW EXECUTE FUNCTION notify_new_job();

A notification is only a doorbell. The worker still runs the claim query with SKIP LOCKED, so if five workers wake up for one job, one gets it and four find nothing.

8. Is polling the jobs table expensive?

Short answer: no, an empty poll is very cheap if you have the right index. The cost to watch is dead rows, not the polling itself. These numbers come from a throwaway Postgres 17 container on a laptop, with 1 million finished jobs in the table and nothing queued. The script to reproduce them is at the end of this section.

What was measured

MeasurementResult
One empty-queue claim query (EXPLAIN ANALYZE)0.057 ms, reading 1 page (8 KB) from memory
10 clients running the claim non-stop for 10 seconds (pgbench)~106,000 polls/second, 0.09 ms average latency
Data written to disk (WAL) by 5 seconds of non-stop empty polls0 bytes
Same empty poll after 50,000 jobs were queued and finished, with autovacuum off450 pages read instead of 1
Same poll after running VACUUMBack to 1 page

Absolute numbers depend on hardware. The ratios are the point: an empty poll is a tiny index lookup, and dead rows are what make it grow.

Why an empty poll is cheap

  • The partial index only holds waiting jobs. CREATE INDEX ... WHERE status = 'queued' leaves the million finished rows out, so with an empty queue Postgres checks one small index page and stops. The size of the table doesn't matter.
  • An UPDATE that matches no row writes nothing. No new row versions, no WAL, no work for vacuum. An empty poll is effectively a read.
  • The page is already in memory. The hot index page stays in Postgres's shared buffers, so there's no disk I/O.

For scale: 10 workers polling once a second is 10 queries per second, roughly 1/10,000 of what this laptop handled.

Where it does get expensive

CauseWhat happens
Dead rows not yet vacuumedWhen a job is claimed or finished, its old row version stays in the index until vacuum removes it. Each poll must visit and skip those entries: 450 pages instead of 1 in the test above. On a busy queue where vacuum falls behind, every poll gets slower.
Too many pollers, too often500 workers polling every 100 ms is 5,000 queries per second and 500 open connections. Connections usually run out before CPU does.
Everyone rushing the same rowWhen a job arrives, every idle worker races for it. SKIP LOCKED keeps this correct (one winner, no waiting), but at large scale it's wasted round trips.
A missing or wrong indexWithout the partial index, each poll scans far more of the table, and the cost grows with the number of finished jobs.

How to keep it cheap

TechniqueEffect
Partial index on queued jobsEmpty polls stay at about 1 page however big the table gets
Aggressive autovacuum on the jobs tableDead entries are cleaned up quickly, so polls don't slow down
Archive or delete finished jobsSmaller table and indexes. Partition by time and drop old partitions at high volume.
Back off when idleAn idle queue costs almost nothing
LISTEN/NOTIFY plus a slow fallback poll (e.g. every 30 s)Instant pickup with almost no polling (see section 7)
One dispatcher per process claiming a few jobs at once (LIMIT 5) and handing them to async tasksOne poller per process instead of one per task
-- vacuum the jobs table after ~1% of rows change, with no throttling
ALTER TABLE jobs SET (
  autovacuum_vacuum_scale_factor = 0.01,
  autovacuum_vacuum_cost_delay   = 0
);
# idle backoff in the worker loop: 1s, 2s, 4s ... capped at 30s; reset after finding a job
delay = 1
while True:
    row = conn.execute(CLAIM, params).fetchone()
    if row is None:
        time.sleep(delay)
        delay = min(delay * 2, 30)
        continue
    delay = 1
    process(row)

For long-running, low-volume jobs such as AI agent runs, plain polling every 1 to 2 seconds with backoff is effectively free. Add LISTEN/NOTIFY only if you need pickup in under a second.

9. A complete Python worker

Uses psycopg 3. Polling with a short sleep, lease and heartbeat, retries with backoff. A learning sketch: add logging, metrics and graceful shutdown for production.

import json, socket, threading, time
import psycopg

DSN = "postgresql://app:app@localhost:5432/app"
WORKER_ID = f"{socket.gethostname()}-{threading.get_ident()}"
LEASE = 60          # seconds
HEARTBEAT = 20      # seconds

CLAIM = """
UPDATE jobs SET status = 'running', attempts = attempts + 1,
                locked_by = %(me)s, locked_until = now() + make_interval(secs => %(lease)s)
WHERE id = (
  SELECT id FROM jobs
  WHERE (status = 'queued' AND run_after <= now())
     OR (status = 'running' AND locked_until < now())
  ORDER BY run_after
  FOR UPDATE SKIP LOCKED
  LIMIT 1)
RETURNING id, payload, attempts, max_attempts;
"""

def heartbeat(job_id, stop):
    with psycopg.connect(DSN, autocommit=True) as conn:
        while not stop.wait(HEARTBEAT):
            conn.execute("UPDATE jobs SET locked_until = now() + make_interval(secs => %s) "
                         "WHERE id = %s AND locked_by = %s", (LEASE, job_id, WORKER_ID))

def handle(payload):
    print("working on", payload)
    time.sleep(5)                      # your real work: run the agent, etc.

def main():
    with psycopg.connect(DSN, autocommit=True) as conn:
        while True:
            row = conn.execute(CLAIM, {"me": WORKER_ID, "lease": LEASE}).fetchone()
            if row is None:
                time.sleep(1)          # queue empty
                continue
            job_id, payload, attempts, max_attempts = row
            stop = threading.Event()
            threading.Thread(target=heartbeat, args=(job_id, stop), daemon=True).start()
            try:
                handle(payload)
                conn.execute("UPDATE jobs SET status = 'done', locked_until = NULL "
                             "WHERE id = %s AND locked_by = %s", (job_id, WORKER_ID))
            except Exception as e:
                conn.execute("""
                    UPDATE jobs SET
                      status = CASE WHEN attempts >= max_attempts THEN 'failed' ELSE 'queued' END,
                      run_after = now() + make_interval(secs => 30 * power(2, attempts)),
                      last_error = %s, locked_by = NULL, locked_until = NULL
                    WHERE id = %s AND locked_by = %s""", (str(e), job_id, WORKER_ID))
            finally:
                stop.set()

if __name__ == "__main__":
    main()

Try it: start Postgres (docker run -e POSTGRES_PASSWORD=app -e POSTGRES_USER=app -p 5432:5432 postgres:17), create the table, insert 10 jobs, then run the worker in two terminals. Each job is printed by exactly one of them. Kill one worker with Ctrl+C mid-job: about 60 seconds later the other one picks that job up.

10. Ready-made options

pgmq: an extension with an SQS-style API

This one is enabled, with CREATE EXTENSION. It must be installed on the server first (it's in some Docker images and some managed providers; check yours).

CREATE EXTENSION pgmq;

SELECT pgmq.create('runs');                              -- creates the queue's tables
SELECT pgmq.send('runs', '{"run_id": "r_123"}');         -- returns msg_id
SELECT * FROM pgmq.read('runs', 30, 1);                  -- hide for 30s, read 1 message
SELECT pgmq.set_vt('runs', 1, 60);                       -- extend visibility (heartbeat)
SELECT pgmq.delete('runs', 1);                           -- done: remove msg_id 1
SELECT pgmq.archive('runs', 1);                          -- or move it to an archive table

Same model as AWS SQS: a read message becomes invisible for the visibility timeout, and reappears if you don't delete it in time.

11. Limits and maintenance

ConcernWhat happensWhat to do
Table bloatEvery UPDATE writes a new row version; old versions are dead rows until vacuum removes them. A busy queue creates many.Delete or archive finished jobs regularly. Tune autovacuum to run more often on the jobs table. For very busy queues, partition by time and drop old partitions.
ThroughputComfortable at hundreds of jobs per second. Beyond that, lock contention and vacuum become the bottleneck.Batch claims (LIMIT 10), keep the hot index small with a partial index, or move to a dedicated broker.
Load on the main databasePolling and job writes compete with your application's queries.Use LISTEN/NOTIFY to cut polling. Put the queue in a separate database if the app database is busy.
ConnectionsEach worker holds a connection.Use a pool. Many async jobs can share one worker process and a few connections.
No fan-outA job goes to one worker. There's no built-in "send this to every subscriber".Use a pub/sub system or a log (Kafka) for events that many services consume.

12. When to use it, and when to move on

Good fitMove to something else
  • You already run Postgres and want no extra infrastructure
  • Jobs must be created atomically with your data
  • Long-running jobs where correctness matters more than speed
  • Up to hundreds of jobs per second
  • You want to query, inspect and fix jobs with SQL
  • Thousands of jobs per second or more → RabbitMQ, SQS, Redis
  • Many services need the same events, or replay → Kafka
  • Complex multi-step flows with timers and approvals → Temporal or Hatchet
  • The queue is measurably hurting the main database

Summary: a table + FOR UPDATE SKIP LOCKED gives you a safe multi-worker queue. Add a lease with heartbeats for long jobs, a reaper for crashed workers, retries with backoff, and optionally LISTEN/NOTIFY for instant pickup. Start here; move to a broker when you've measured a reason to.
