1. Why we need Redis

The problem it solves

A product page needs the product, its price, stock, reviews summary and the user's cart. Each comes from a database query taking 5–50 ms. Under load, the same queries run thousands of times a second for the same popular products, and the database becomes the bottleneck. Meanwhile, you also need a counter of login attempts per IP, a leaderboard, a place to keep sessions shared by 20 web pods, and a way to make sure only one pod runs the nightly job.

20 web pods ──▶ database   (same 100 queries, 5,000 times/s; 30 ms each)
            ──▶ ??? shared sessions
            ──▶ ??? rate limit per IP
            ──▶ ??? "only one pod runs this"

What Redis changes

Redis is an in-memory data structure server. Every read and write is served from RAM, typically in well under a millisecond, and every value has a type with its own atomic operations: counters, lists, sets, sorted sets, hashes, streams. So it's not only a cache; it's a toolbox of shared, fast, atomic building blocks for all your pods.

PropertyWhat it gives you
SpeedSub-millisecond operations; one instance handles on the order of 100,000+ simple operations per second.
Data structuresStrings, hashes, lists, sets, sorted sets, streams, bitmaps, HyperLogLog, geo, and (Redis 8 / modules) JSON, search and vectors.
Atomicity for freeCommands run one at a time, so INCR, SET NX, ZADD never race. Lua scripts and MULTI run several steps atomically.
ExpiryAny key can have a TTL; Redis deletes it for you. Perfect for caches, sessions, rate-limit windows and locks.
Shared stateAll pods see the same data, unlike in-process memory.
SimplicityA single binary, a text protocol, clients for every language.
One sentence: Redis is shared, very fast, in-memory data structures with atomic operations and expiry, used as a cache and as the building blocks for counters, sessions, rate limits, leaderboards, locks and light queues.

Five facts explain most of Redis's behaviour:

  1. Everything is in RAM. Memory is the capacity limit and the cost.
  2. One command runs at a time. That's why it's atomic, and why one slow command (KEYS *, a huge DEL, a long Lua script) freezes every client.
  3. Durability is optional and asynchronous. By default you can lose recent writes on a crash, and replicas lag the primary.
  4. Data structures are the API. Choosing the right type turns a hard problem into one command.
  5. Expiry is the cleanup mechanism. Keys without TTLs live forever and eventually fill memory.

3. Practical use cases

3.1 Caching (cache-aside)

The number one use. Read: GET from Redis; on a miss, query the database, SET key value EX 300, return. Write: update the database, then DEL the cache key. Cuts database load by 90%+ for read-heavy apps.

What matters: TTLs with jitter, stampede protection, invalidation, what happens when Redis is down (see 5.2).

3.2 Session store

Web sessions as hashes with a TTL that's refreshed on each request. Any pod can serve any user. What matters: persistence and a replica, because losing Redis logs everyone out.

3.3 Rate limiting

Fixed window: INCR rl:{ip}:{minute} + EXPIRE. Sliding window: a sorted set of request timestamps, trimmed with ZREMRANGEBYSCORE. Token bucket: a small Lua script. Used by API gateways, login protection, partner API quotas.

3.4 Counters and real-time analytics

Page views, likes, stock counts with INCR/HINCRBY; unique visitors with HyperLogLog (PFADD/PFCOUNT, ~12 KB per counter with ~0.81% error); daily activity with bitmaps. Flushed periodically to the database for long-term storage.

3.5 Leaderboards and rankings

A sorted set: ZINCRBY leaderboard 10 user:42, ZREVRANGE leaderboard 0 9 WITHSCORES for the top 10, ZREVRANK for "your position". Logarithmic time even for millions of players.

3.6 Queues and background jobs

Lists (LPUSH + BLMOVE into a processing list for reliability) power Sidekiq, RQ, BullMQ, and Celery's Redis broker. Streams (XADD, XREADGROUP, XACK, XAUTOCLAIM) add consumer groups and acks. Good for moderate volume where Redis is already in place (see 5.7 for the limits).

3.7 Distributed locks and leader election

SET lock:nightly-job <random-token> NX PX 30000: only one pod gets it. Release only if you still hold it (check the token in a Lua script). Fine for efficiency ("don't run twice"), not for correctness without fencing (see 5.8).

3.8 Pub/Sub and real-time fan-out

Chat messages, live dashboards, WebSocket fan-out across pods (Socket.IO and similar use a Redis adapter), "invalidate this cache key" broadcasts. Fire-and-forget: a disconnected subscriber misses messages.

3.9 Deduplication and idempotency keys

SET idem:{request_id} 1 NX EX 86400 returns whether this request was already seen; a set of processed message ids makes queue consumers idempotent. Used in payment APIs and webhook receivers.

3.10 Geo, feature flags, and vector search

Geo commands for "nearby drivers"; hashes for feature flags read on every request; and with Redis 8 (or Redis Stack / modules) JSON documents, secondary indexes and vector similarity search for semantic caching and RAG retrieval. Online feature stores (Feast's Redis online store) keep ML features here for millisecond lookups.

5. An experienced engineer's notebook

What follows is written in the voice of someone who has designed, run and been paged for Redis over many years. Each note is a lesson that usually costs an incident to learn.

5.1 Keys, values and data modelling

Name keys with a clear scheme. <app>:<entity>:<id>[:<field>], for example shop:product:9:price. It makes SCAN MATCH, debugging, memory analysis and later migration possible. Keep keys short but readable; at hundreds of millions of keys, key length is real memory.
Every key needs an owner and a lifetime. Ask for every key pattern: who writes it, who deletes it, and what its TTL is. Keys "nobody deletes" are the most common cause of slow memory growth. If a key must live forever, document why.
Avoid big keys. A single hash, list, set or sorted set with millions of members, or a string of tens of MB, makes every operation on it slow, blocks the server on DEL, unbalances a cluster shard and spikes network use. Split by bucket (followers:42:0..15), and delete big keys with UNLINK (frees memory in the background). Find them with redis-cli --bigkeys / --memkeys.
Watch for hot keys. One key read 200,000 times a second (a celebrity's profile, a global config) maxes out one thread on one shard while others idle. Fix with client-side caching (Redis 6+ tracking, or a short in-process cache), or by copying the value under several keys and reading one at random. Find them with redis-cli --hotkeys (needs an LFU eviction policy) or by sampling MONITOR briefly on a non-critical replica.
Pick the type for the operations, not the shape. Need ranking? Sorted set. Need membership? Set. Need to update one field of an object? Hash, not a JSON string you rewrite whole. Small hashes, lists and sets use compact encodings (listpack) that are much more memory-efficient, so many small hashes beat one giant one.
Serialize deliberately. JSON is readable; MessagePack or Protobuf are smaller and faster. Include a version in the value or key (v2:) so a deploy that changes the format doesn't crash on old cached values. Compress large values on the client.
Don't use multiple numbered databases. SELECT 3 looks like namespacing, but databases share one thread and memory, can't be limited separately, and Redis Cluster supports only database 0. Use key prefixes, or separate instances for workloads that need isolation (cache vs queue vs sessions).

5.2 Caching done right

Cache-aside, delete on write. On update: write the database first, then DEL the key (don't SET the new value; two concurrent writers can leave the older value in the cache). The next read repopulates it. Accept that there's a short window of staleness, and set a TTL as the safety net for any invalidation you miss.
Add jitter to TTLs. Keys written together with the same TTL expire together, and the database gets every miss at the same moment. Use TTL = base + random(0, 10%).
Protect against stampedes. When a hot key expires, a thousand requests miss at once and all query the database (thundering herd). Options: a short lock so only one request rebuilds (SET rebuild:key 1 NX EX 10, others wait briefly or serve stale); refresh ahead of expiry in the background; or store a "soft expiry" inside the value and serve stale while one request refreshes.
Cache misses too. Requests for things that don't exist (deleted products, bots probing ids) miss every time and hit the database (cache penetration). Cache a "not found" marker with a short TTL, or check a Bloom filter first.
Plan for Redis being down. A cache is an optimization; the app must survive without it. Use short client timeouts (tens of ms), a circuit breaker, and fall back to the database at a limited rate. And know the scary case: if the database can't handle full traffic without the cache, then Redis isn't "just a cache" anymore, it's critical infrastructure. Treat it that way (replicas, failover, warm-up plans).
Warm up after a cold start. A restarted or new cache sends 100% of traffic to the database. Keep persistence on cache instances if a cold start would hurt, or pre-load hot keys, or ramp traffic gradually.

5.3 Memory and eviction

Always set maxmemory. The default is 0 (no limit, lab). Without a limit Redis grows until the OS or Kubernetes OOM-kills it, which loses everything not yet persisted. Set it to roughly 60–75% of the machine's or container's memory, leaving room for fork copy-on-write, client buffers and fragmentation.
Choose the eviction policy for the workload. The default is noeviction (lab): when full, writes fail with OOM command not allowed. That's right for queues, sessions and anything you can't lose, and wrong for a cache. For caches use allkeys-lru or allkeys-lfu (LFU keeps popular keys better). volatile-* policies only evict keys with a TTL. Mixing a cache and important data in one instance with one policy is a classic mistake: separate them.
Know where memory goes. INFO memory: used_memory (data), used_memory_rss (what the OS sees), mem_fragmentation_ratio (rss ÷ used; above ~1.5 means wasted memory; consider activedefrag yes). MEMORY USAGE key for one key. Client output buffers (slow pub/sub subscribers, replicas) can quietly use gigabytes.
Expired keys aren't deleted instantly. Redis removes them when accessed, plus a background sampling process. Millions of keys expiring at once costs CPU. Spread expiry times.

5.4 Performance: the single thread

Never run KEYS * in production. It walks the whole keyspace in one blocking command; with 50 million keys, Redis freezes for seconds and every client times out. Use SCAN with a cursor (and HSCAN, SSCAN, ZSCAN). Many teams rename or disable KEYS, FLUSHALL, FLUSHDB and DEBUG via ACLs.
Watch O(N) commands. HGETALL, SMEMBERS, LRANGE 0 -1, ZRANGE 0 -1, DEL on a big key, SORT, SUNION on large sets. Fine on small values, server-freezing on big ones. Check SLOWLOG GET (logs commands over 10 ms by default, lab slowlog-log-slower-than 10000 µs).
Pipeline round trips. 1,000 GETs one by one = 1,000 network round trips; pipelined (or MGET) = about one. Network latency, not Redis, is usually the bottleneck. Batch everything you can.
Lua scripts and MULTI are atomic, and blocking. A script runs to completion with nothing else served. Keep scripts short and bounded. A script that loops over a growing key gets slower every day until it's an outage. Redis 7 functions (FUNCTION LOAD) are the managed successor to EVAL scripts.
Scaling CPU. One Redis process uses about one core for commands. io-threads (1 by default, lab) offloads network reads/writes and helps with many clients and large replies. Beyond one core of command work, shard (Redis Cluster) or use read replicas for read-heavy, stale-tolerant traffic.
Latency has OS causes too. Disable Transparent Huge Pages (latency spikes during fork), avoid swap (Redis in swap is unusable), put clients close to the server (same zone), and use LATENCY DOCTOR / redis-cli --latency to measure.

5.5 Persistence and durability

OptionHow it worksYou can lose
NonePure in-memoryEverything on restart
RDB snapshotsPeriodic full snapshot via fork(). Lab default: save 3600 1 300 100 60 10000Everything since the last snapshot (minutes)
AOF, appendfsync everysecLog every write, fsync once a second (off by default, lab appendonly no)About 1 second

Fork needs memory. RDB snapshots and AOF rewrites fork() the process. Pages written during the snapshot are copied (copy-on-write), so a write-heavy instance can briefly need up to double its memory. Set vm.overcommit_memory=1 on Linux (Redis warns otherwise) and leave headroom under maxmemory, or the fork fails or the OOM killer strikes mid-snapshot.
Replication doesn't make writes durable. Replication is asynchronous: the primary acknowledges a write before replicas have it. If the primary dies, a promoted replica may be missing the last writes. WAIT 1 100 waits for replicas but still doesn't make Redis a strongly consistent database.
Test restores. Back up RDB files off the machine (S3) on a schedule, and actually restore one now and then. A backup you've never restored is a hope, not a backup.
Danger: a primary with no persistence and auto-restart. If it restarts empty, its replicas faithfully sync the empty dataset and wipe themselves. If you run without persistence, don't let the primary auto-restart before failover happens.

5.6 Replication, Sentinel and Cluster

SetupWhat it givesUse when
Single instanceSimplicityDev, or a cache you can lose
Primary + replicasRead scaling, a warm copyRead-heavy, manual failover acceptable
Sentinel (3+ sentinels)Automatic failover for one primary; clients ask Sentinel who the primary isData fits one machine, need HA
Redis ClusterSharding over 16384 hash slots, each shard with replicas and automatic failoverData or throughput beyond one machine
Cluster changes your code. Keys are spread by CRC16(key) mod 16384. Multi-key commands (MGET, MULTI, Lua with several keys, SUNION) work only if all keys are in the same slot, otherwise CROSSSLOT error. Use hash tags, {user:42}:cart and {user:42}:profile, to force related keys together, but too much tagging creates a hot shard. (Demonstrated in tools/redis/cluster/examples/crossslot_and_hashtags.py.)
Use a cluster-aware client. It caches the slot map and follows MOVED/ASK redirects during resharding and failover. Point it at several seed nodes.
Failover takes seconds and can lose writes. Expect a few seconds of errors during failover (node timeout + election), with retries in clients. Writes acknowledged by the old primary but not yet replicated are lost. Design callers to tolerate both.
Reading from replicas means stale reads. Replica lag is usually milliseconds, but under load or after a resync it can be seconds. Read-your-own-writes paths must use the primary.
Size the replication backlog. If a replica disconnects briefly and the backlog (1 MB by default, lab repl-backlog-size 1048576) has been overwritten, it needs a full resync: a fork and a full RDB transfer. On busy primaries raise it to hundreds of MB to survive short network blips.

5.7 Redis as a queue or message bus

MechanismStored?Ack / redeliveryFits
Pub/SubNo: only connected subscribers get itNoLive notifications, cache-invalidation signals, WebSocket fan-out
List + BRPOPYesNo: a crash after pop loses the jobSimple, loss-tolerant jobs
List + BLMOVE to a processing listYesManual: a reaper requeues stuck itemsReliable simple queues (what many job libraries do)
Streams + consumer groupsYes, until trimmedYes: XACK, pending list, XAUTOCLAIM for stuck messagesKafka-like light event streams and work queues
Pub/sub loses messages, by design. A subscriber that disconnects for one second misses that second. A slow subscriber's output buffer grows until the client is killed (lab: pubsub 32mb 8mb 60: hard limit 32 MB, or 8 MB for 60 s). Use it only where loss is fine.
Trim streams. Streams grow forever unless you trim: XADD ... MAXLEN ~ 1000000 or MINID. The ~ makes trimming cheap. Also watch the pending entries list (XPENDING): messages delivered but never acked stay there and need XAUTOCLAIM to move to a live consumer.
Know the ceiling. A Redis queue lives in RAM, replication is async, and a failover can lose or duplicate messages. That's fine for many background-job systems (Sidekiq and BullMQ run huge workloads this way), but if a lost job means lost money, use a broker with real durability or make jobs reconstructable from the database.

5.8 Locks and coordination

The correct single-instance lock. Acquire: SET lock:res <unique-token> NX PX 30000. Release: a Lua script that deletes the key only if its value is still your token. Never DEL blindly: your lock may have expired and now belong to someone else.
A lock with a TTL can expire while you're still working. A GC pause, a slow network call, a stalled VM, and your lease is gone; another client takes the lock; both now run. Extend the lease while working (watchdog), and for correctness pass a fencing token (an increasing number from INCR) to the resource you protect, which rejects older tokens. The same idea is tested in Postgres as a queue with real pods.
Redlock is debated. The multi-instance Redlock algorithm is widely used, and widely criticized (Martin Kleppmann's analysis) for relying on timing assumptions. Practical stance: Redis locks are great for efficiency (avoid duplicate work); for correctness (never double-charge), use database constraints, transactions, or etcd/ZooKeeper with fencing.

5.9 Clients and connections

Use a connection pool and set timeouts. Connect and command timeouts in tens or hundreds of milliseconds, not the library's default (sometimes none). Without timeouts, a slow Redis makes every web thread hang, and the outage spreads.
Retry carefully. Retrying a read is safe. Retrying a write like INCR after a timeout may apply it twice (the first may have succeeded). Use idempotent writes (SET with a value) or accept the risk knowingly.
Connection storms. 500 pods × a pool of 50 = 25,000 connections; maxclients is 10000 by default (lab). Size pools to real concurrency, and watch connected_clients and rejected_connections. After a Redis restart, all clients reconnect at once; jittered backoff helps.
Blocking commands need their own connections. BLPOP, XREAD BLOCK and SUBSCRIBE hold a connection while waiting. Don't take them from the pool your web requests use.

5.10 Security

Never expose Redis to the internet. Unprotected Redis instances are found and abused within minutes (data wiped, crypto-miners installed via config tricks). Bind to private interfaces, keep protected mode on, put it behind network policies or security groups.
Use ACLs (Redis 6+). A user per application with only the commands and key patterns it needs (~shop:*, -@dangerous). Disable the default user or give it a strong password. TLS in transit for anything crossing a network you don't fully control.

6. Design review checklist

  1. Is Redis a cache (losable) or holding data that must survive? Then which persistence and HA?
  2. What are the key patterns, their owners and their TTLs?
  3. Any key that can become big (millions of members, MBs) or hot (very high request rate)?
  4. maxmemory set, with headroom for fork and buffers? Eviction policy right for this data?
  5. Cache: how is it invalidated on writes? Stampede protection? TTL jitter? Negative caching?
  6. What happens to the app when Redis is slow or down? Timeouts, circuit breaker, fallback?
  7. Can the database survive a cold cache?
  8. Any O(N) commands or scripts on growing data in hot paths?
  9. Cluster: are multi-key operations in the same slot (hash tags)? Is the client cluster-aware?
  10. Queues/streams: what if a consumer crashes mid-job? Trimming? Pending-entry reclaim?
  11. Locks: what if the lock expires during work, or a failover happens? Fencing?
  12. Connection pool size × number of pods vs maxclients?
  13. Network exposure, ACL user per app, TLS?
  14. Alerts on memory, evictions, latency, replication and persistence status?
