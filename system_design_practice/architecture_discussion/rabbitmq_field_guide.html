Applies to RabbitMQ 4.x (the lab broker lab-rabbitmq runs 4.1.8; numbers marked "lab" were read from it with rabbitmqctl environment). Python examples use pika. 1. Why we need RabbitMQ

The problem it solves

A web app needs to resize an uploaded image, send a welcome email and generate a PDF invoice. Doing it inside the HTTP request makes users wait, and if the email server is slow, the whole request times out. Doing it in a background thread loses the work when the pod restarts. Writing your own "jobs" table works for a while, then you need retries, delays, priorities, routing to different worker types, and many workers that never take the same job.

web request ──▶ resize image (3 s)       user waits 3 + 2 + 5 seconds
            ──▶ send email (2 s)         email server down = request fails
            ──▶ build PDF (5 s)          pod restarts mid-way = work lost
                                         traffic spike = web servers overloaded

What RabbitMQ changes

RabbitMQ is a message broker: it accepts a message, stores it in a queue, and hands it to exactly one worker that is ready, waiting for that worker to confirm (ack) before deleting it. If the worker dies, the message goes to another worker.

web ──publish "resize 42"──▶ [exchange] ──route──▶ [queue images] ──▶ worker A (busy)
                                                                  ──▶ worker B (takes next)
                                          ──route──▶ [queue emails] ──▶ email worker
PropertyWhat it gives you
Work distributionMany workers share a queue; each message goes to one of them. Add workers to go faster, with no partition limit.
Reliable hand-offMessages are deleted only after an ack. A crashed worker's message is redelivered.
Flexible routingExchanges route by exact key, pattern (order.*.eu), headers, or copy to every bound queue.
Per-message featuresTTLs, dead-lettering, priorities, delivery limits, request/reply, single active consumer.
Back-pressurePrefetch limits how much each worker holds; the broker slows publishers when memory or disk run low.
Low latencyMessages are pushed to consumers as they arrive; sub-millisecond hand-off is normal.
Many protocolsAMQP 0-9-1 (most clients), AMQP 1.0 (native in 4.x), MQTT, STOMP, and the stream protocol.
One sentence: RabbitMQ is a smart broker that routes messages into queues and hands each one to a single ready worker, deleting it only when the worker says it's done.

2. The mental model in one page

publisher ──▶ exchange ──(bindings)──▶ queue ──▶ consumer
              (router)   rules          (buffer)   (ack / nack)

exchange types
  direct   routing key == binding key        "email"         → queue emails
  topic    pattern match, * = 1 word, # = 0+ "order.*.eu"    → queue eu-orders
  fanout   copy to every bound queue          (key ignored)   → all subscribers
  headers  match on message headers           x-match=all/any
  ""       default exchange: routing key = queue name (what "publish to a queue" really does)
WordMeaning
Connection / channelA TCP connection to the broker; channels are lightweight virtual connections inside it. Open one connection per process, one channel per thread.
ExchangeReceives published messages and routes them. Stores nothing.
QueueStores messages until a consumer acks them. The only place messages live.
BindingA rule linking an exchange to a queue (with a key or pattern).
Routing keyA string the publisher attaches; exchanges match bindings against it.
Ack / nack / rejectConsumer says done (delete it), failed (requeue or dead-letter), or refused.
Prefetch (QoS)Max un-acked messages the broker sends one consumer at a time.
Publisher confirmThe broker's ack to the publisher that it has safely stored a message.
Dead-letter exchange (DLX)Where a queue sends messages that were rejected, expired, overflowed or exceeded a delivery limit.
VhostAn isolated namespace of exchanges, queues and permissions on one broker (per app or tenant).

Five facts explain most of RabbitMQ's behaviour:

  1. Publishers send to exchanges, never directly to queues. An unroutable message is silently dropped unless you ask otherwise.
  2. The broker tracks every message's state. That's what makes per-message ack, retry and TTL possible, and why it's slower than Kafka at extreme volume.
  3. A queue is happiest when it's nearly empty. RabbitMQ is a buffer for in-flight work, not a database. Long queues cost memory, disk and recovery time.
  4. Each queue is one process on one node. One queue has a throughput ceiling; scale by using more queues.
  5. Two acks, two directions. Publisher confirms protect publisher → broker; consumer acks protect broker → consumer. Reliability needs both.

3. Practical use cases

3.1 Background job queues (task queues)

The most common use. Web app publishes "send email", "resize image", "generate report"; a pool of workers processes them. Celery (Python), Sidekiq-style libraries, MassTransit (.NET), Spring AMQP, and many others sit on RabbitMQ.

What matters: manual acks, prefetch, idempotent workers, retries with backoff, DLQ, and a consumer_timeout above your longest job.

3.2 Decoupling microservices with commands

Service A tells service B to do something ("ReserveStock", "ChargeCard") without waiting synchronously. B can be down for a few minutes and catch up. Unlike Kafka events, these are often commands with one intended receiver.

3.3 Pub/sub notifications

A fanout or topic exchange copies an event ("UserSignedUp") to every subscribing service's queue: welcome email, CRM sync, analytics. Each subscriber has its own durable queue, so it doesn't miss messages while restarting. (Seen in lab lesson 02.)

3.4 Routing by content

Topic exchanges route order.created.eu to EU workers, order.*.us to US workers, #.priority to a fast lane. Useful for region, tenant, severity or type-based routing without code in the publisher.

3.5 Load levelling and traffic smoothing

A burst of 50,000 requests arrives in a minute; the downstream system (a legacy API, a rate-limited partner, a GPU inference server) can handle 500 a second. The queue absorbs the spike and workers drain it at a safe rate.

3.6 Request/reply (async RPC)

A client publishes a request with reply_to and correlation_id; the server replies to that queue. RabbitMQ's direct reply-to (amq.rabbitmq.reply-to) avoids creating a queue per request. Useful for spreading compute-heavy calls over a worker pool.

3.7 Delayed and scheduled work

"Retry in 5 minutes", "cancel the unpaid order after 30 minutes": a message with a TTL in a waiting queue that dead-letters back to the work queue when it expires, or the delayed-message plugin.

3.8 IoT and device messaging

RabbitMQ's MQTT support (much improved in 3.12+ / 4.x) lets devices connect with MQTT while backend services consume the same messages over AMQP.

3.9 Streams for replay and large fan-out

Since 3.9, RabbitMQ streams are append-only logs (like a Kafka partition) inside RabbitMQ: non-destructive reads, replay from an offset, many consumers. Super streams add partitioning. Useful when you want a little Kafka-style behaviour without a second system.

5. An experienced engineer's notebook

What follows is written in the voice of someone who has designed, run and been paged for RabbitMQ systems over many years. Each note is a lesson that usually costs an incident to learn.

5.1 Designing exchanges, queues and messages

Publish to exchanges you own, consume from queues you own. The publisher declares its exchange (orders, topic type). Each consuming service declares its own queue and binding (billing.orders bound to order.created.*). The publisher never knows who listens; consumers can be added without touching it. Don't publish everything to the default exchange.
Name things predictably. Exchanges by domain (orders), queues by <consumer-service>.<purpose> (billing.order-created), DLQs with a suffix (billing.order-created.dlq). Use one vhost per application or environment, not per developer whim.
Declare topology in code or config, idempotently. Every service declares the exchanges, queues and bindings it needs at startup with the same arguments. Changing arguments of an existing queue (type, TTL, DLX) fails with PRECONDITION_FAILED; you must create a new queue and migrate. Policies (rabbitmqctl set_policy) let you change many settings (DLX, max length, TTL) without redeclaring, so prefer them for operational settings.
Use quorum queues for anything important. Durable, replicated over 3 nodes with Raft, with a delivery limit for poison messages. Classic mirrored queues were removed in 4.0. Use classic queues only for temporary, exclusive or truly disposable data. See 5.5.
Never let a queue grow without limit. Set x-max-length or x-max-length-bytes with overflow=reject-publish (publishers get nacked, so they know) or drop-head (oldest dropped, possibly dead-lettered) depending on whether losing old or new messages is worse. An unbounded queue is a memory alarm waiting to happen.
Messages: small, self-describing, with ids. Set message_id (deduplication), content_type, timestamp, type, a correlation/trace id in headers, and a schema version. Keep bodies to KBs. The server rejects messages over max_message_size (16 MiB on the lab broker), but anything over ~1 MB already hurts. For big payloads, send a link.
Mark messages persistent and queues durable, or neither matters. A durable queue holding transient messages loses them on restart. With quorum queues all messages are persisted anyway, which is one less thing to get wrong.
Don't create a queue per user or per request. Thousands of queues cost memory, metadata and management-UI pain. Use routing keys or headers in fewer queues; for RPC use direct reply-to. If you need per-tenant fairness, a modest number of queues (one per tier or shard) with round-robin consumers works better.
Exclusive and auto-delete queues are for temporary consumers. They vanish when the connection closes, which is right for an RPC reply queue or a live dashboard, and wrong for anything that must survive a restart.

5.2 Publishers

Turn on publisher confirms. Without them, basic_publish is fire-and-forget: a message can be lost if the broker fails, the connection drops, or memory alarms block you, and your code never knows. With confirms, the broker acks each message once it's stored (on a quorum queue: on a majority of replicas). Confirm in batches or asynchronously for throughput; one-by-one synchronous confirms are slow.
Detect unroutable messages. If no binding matches, the exchange drops the message silently, and the publisher still gets a confirm. Set mandatory=true to get it returned, or give the exchange an alternate exchange that collects unroutable messages into a queue you monitor. Typos in routing keys are a classic silent data-loss bug.
One long-lived connection, many channels. Connections are expensive (TCP + TLS + auth + memory on the broker); opening one per publish is how you take a cluster down with "connection churn". Keep a connection per process and a channel per thread. Channels are not thread-safe; never share one across threads.
Handle connection loss and the "blocked" state. Networks drop. Use the client's automatic recovery (or reconnect with backoff) and re-declare topology. When the broker hits a memory or disk alarm, it blocks publishing connections; publishes hang. Listen for connection.blocked and stop accepting work upstream instead of piling up threads.
Don't publish and consume on the same connection. Flow control throttles a connection that publishes too fast; if your consumers share it, they slow down too, which makes the queue grow, which makes flow control worse.
Database + message = outbox. "Save to DB, then publish" eventually publishes a message for a rolled-back transaction or forgets to publish for a committed one. Write the message to an outbox table in the same transaction and have a relay publish it with confirms. The same pattern as Kafka; the problem is the dual write, not the broker.

5.3 Consumers

Manual acks, after the work is done. auto_ack=True means the broker deletes the message the moment it's sent, so a crash loses it. Ack after processing (and after committing any database transaction). That gives at-least-once delivery. (Seen in lab lesson 01: kill a worker mid-job and the job is redelivered.)
Always set prefetch. Without basic_qos(prefetch_count=N) the broker pushes the whole queue to the first consumer, which runs out of memory while other workers sit idle. Rules of thumb: long or uneven jobs → prefetch 1 (fair dispatch); fast small messages → 20–300 to keep the pipe full. Measure; it's the most important consumer setting.
Make handlers idempotent. Redelivery happens after crashes, network blips (an ack lost in flight), consumer timeouts and failovers. Check message_id against a processed-ids table, use upserts, use idempotency keys on external calls. The redelivered flag hints at a possible duplicate but is not a guarantee either way.
Mind the consumer timeout. If a message stays un-acked longer than consumer_timeout (30 minutes, lab default 1800000 ms), the broker closes the channel with PRECONDITION_FAILED and requeues the message. Long jobs either raise it (per queue via policy/argument in recent versions), or ack early and track progress elsewhere.
Heartbeats keep connections honest. Heartbeats (60 s negotiated by default on the lab broker) detect dead TCP connections. A consumer that blocks its I/O thread with CPU-heavy work in a single-threaded client (classic pika BlockingConnection) misses heartbeats and gets disconnected mid-job. Do heavy work in another thread and ack back through the connection's thread-safe callback, or use an async client.
Ordering is per queue, and fragile. One queue + one consumer + no requeues = order kept. Several consumers, prefetch > 1, or a nack-requeue all reorder messages. If order matters, use single active consumer (one consumer reads, others stand by), or shard into several queues by key with the consistent-hash exchange, one consumer each.
Scale consumers, but watch the queue's ceiling. More consumers on one queue add throughput until the queue process itself is the bottleneck (a single queue typically tops out in the tens of thousands of messages per second, depending on size, persistence and type). Beyond that, shard across several queues.
Shut down gracefully. On SIGTERM: stop consuming (basic_cancel), finish in-flight messages, ack them, then close. Kubernetes gives 30 seconds by default; set terminationGracePeriodSeconds to cover your longest job, or accept redelivery.

5.4 Failures, retries and dead letters

Never nack-with-requeue in a loop. basic_nack(requeue=True) puts a failing message straight back at the head of the queue. It's redelivered immediately, fails again, forever: 100% CPU, no progress, logs exploding. On quorum queues the delivery limit (20 by default since 4.0) eventually dead-letters it; on classic queues nothing stops it.
Every work queue gets a dead-letter exchange. Messages are dead-lettered when rejected without requeue, when they expire (TTL), when the queue overflows (drop-head), or when they pass the delivery limit. The DLX routes them to a DLQ with an x-death header saying why, how many times and from where. (Seen in lab lesson 03.)
Retry with backoff using TTL queues. The standard pattern: on failure, publish to work.retry.30s (a queue with x-message-ttl=30000 and DLX pointing back to the work exchange); after 30 s it flows back automatically. Chain 30 s → 5 min → 30 min, count attempts in a header, and send to the final DLQ after the last. Queue-level TTL only expires messages at the head of the queue, so use one queue per delay, not mixed per-message TTLs in one queue.
Transient vs permanent failures. Database timeout or HTTP 503: retry with backoff. Malformed message, validation error, "customer doesn't exist": retrying won't help, dead-letter it right away with the error in a header.
Watch and drain the DLQ. Alert on DLQ depth above zero. Keep a small tool (or use the shovel plugin / management UI "move messages") to re-publish fixed messages to the work queue. A DLQ nobody reads is silent data loss with extra steps.
The delayed-message plugin has limits. It's convenient for "deliver in 10 minutes", but delayed messages are stored on one node only, outside normal queue replication, and it isn't designed for millions of pending delays. For critical scheduling, use TTL+DLX queues or a database scheduler.

5.6 Running the cluster

Three nodes, odd numbers. Quorum queues need a majority: 3 nodes tolerate 1 failure, 5 tolerate 2. Two nodes is worse than one (losing either loses the majority). Spread nodes over availability zones. Clients connect through a load balancer or a list of all nodes.
Know the alarms. When memory use passes vm_memory_high_watermark (0.6 of RAM, lab) or free disk drops below disk_free_limit (50 MB, lab), the broker blocks all publishers cluster-wide until it recovers. 50 MB is far too low for production; set it to at least the RAM size (or a ratio like disk_free_limit.relative = 1.5). In containers, make sure RabbitMQ sees the container memory limit, not the host's.
Network partitions are real. In a split, nodes may disagree. Quorum queues handle this with Raft (the minority side stops serving those queues). For the rest, cluster_partition_handling = pause_minority is the usual safe choice. Never stretch one cluster across regions; use federation or shovel between regional clusters.
Spread queue leaders. Each quorum queue has a leader node doing most of the work. If all leaders end up on one node (after restarts), that node is overloaded. Use queue_leader_locator=balanced and rabbitmq-queues rebalance after maintenance.
Upgrades: rolling, with feature flags. Upgrade one node at a time, waiting for quorum queues to be fully replicated (rabbitmq-queues check_if_node_is_quorum_critical) before stopping the next. Enable all stable feature flags after each upgrade; you can't skip too many versions at once. 4.0 removed classic mirroring, so migrate mirrored queues to quorum before upgrading from 3.x. The metadata store is moving from Mnesia to Khepri (Raft-based) in 4.x; read the release notes for your target version.
Kubernetes: use the Cluster Operator. The RabbitMQ Cluster Kubernetes Operator and Messaging Topology Operator manage StatefulSets, peer discovery, TLS, users, vhosts, queues and policies as resources. Give each node a persistent volume and a PodDisruptionBudget so drains don't take out two nodes at once.
Security basics. Delete or disable the guest user (it's only allowed from localhost anyway), one user per application with permissions limited to its vhost and resources, TLS for clients and between nodes, and keep the management UI off the public internet.

6. Design review checklist

  1. Is this a job queue / command (RabbitMQ fits) or an event history many teams replay (Kafka fits)?
  2. Which exchange type, and what routing keys? Who owns the exchange, who owns each queue?
  3. Quorum, classic or stream queue, and why?
  4. Publisher confirms on? What happens to unroutable messages (mandatory / alternate exchange)?
  5. Manual acks after processing? What prefetch, and why that number?
  6. What happens if a message is delivered twice?
  7. How are failures retried, with what backoff, how many times? Where do permanent failures go, and who watches that DLQ?
  8. Worst-case processing time vs consumer timeout, heartbeat and pod shutdown grace?
  9. Max queue length and overflow behaviour?
  10. Does ordering matter? If yes, how is it guaranteed (single active consumer, sharding)?
  11. Message size, schema, ids, timestamps, trace ids?
  12. How does the producer avoid dual writes (outbox)?
  13. Connections and channels: pooled and long-lived? Reconnection and topology recovery?
  14. Alerts on depth, consumers = 0, DLQ > 0, and broker alarms?
