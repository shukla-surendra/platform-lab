Long-running agent jobs in a multi-tenant system

How to take a FastAPI endpoint that runs an agent inside one HTTP request and turn it into submit-and-poll background jobs that can run for minutes or hours, survive crashes and deploys, treat tenants fairly, and run on any cloud. Each section lays out the options and their trade-offs before recommending one.

1. Why the current setup breaks

Today the agent runs inside the request handler: the client opens a connection, FastAPI runs the agent, and the response is sent when it finishes. That's fine for a 10-second ReAct loop. A deep agent (planning, subagents, a critic pass) can take 5 to 60+ minutes, and then things fail:

  • Timeouts along the path. Load balancers, ingress controllers, API gateways and browsers each have idle or total timeouts (often 30 to 120 seconds by default). Any one of them can cut the connection.
  • The work dies with the connection or the pod. If the client disconnects, or the pod is restarted for a deploy, the run is lost along with all the tokens already spent.
  • No retry story. The client can't tell "still working" from "dead", so it retries and starts a second, duplicate run.
  • The API can't scale. Each in-flight run holds a web worker's connection and memory. A burst of long jobs from one tenant can fill every worker and block short requests for all tenants.

FastAPI BackgroundTasks doesn't fix this. It runs the work after the response, but in the same process. It has no persistence, no retries, and no status, and the work is lost on restart. Use it for "send an email after responding", not for an hour-long agent.

2. Requirements

Functional

  • A tenant's user or system submits an agent run and immediately gets back a run_id.
  • The caller can check status and progress at any time, from any client, without holding a connection open.
  • The caller can fetch the result when it's done, and cancel a run in progress.
  • Optional: be notified on completion (webhook) and stream live progress (SSE).
  • Optional: human-in-the-loop, where the agent pauses for approval and then resumes.

3. The core pattern: async request-reply

This is a standard pattern (sometimes called "async request-reply" or "202 + status endpoint"). The work is split into three separate, short HTTP exchanges:

  1. Submit. POST /v1/runs validates the input, writes a runs row with status queued, enqueues the run_id, and returns 202 Accepted with a Location: /v1/runs/{id} header. This takes milliseconds.
  2. Execute. A separate worker process picks up the job, runs the agent, writes progress and checkpoints as it goes, and finally stores the result and sets the status to succeeded or failed.
  3. Check. The client calls GET /v1/runs/{id} whenever it likes. The response includes a Retry-After header suggesting when to ask again. When the run is finished, the response contains the result or a link to it.

The tenant is never part of the URL or the body. It's taken from the authenticated token, so a caller can't ask for another tenant's run by changing an ID. A run that belongs to another tenant returns 404, not 403, so its existence isn't revealed.

6. Run lifecycle and data model

CREATE TABLE runs (
  id               text PRIMARY KEY,               -- ULID: sortable, not guessable
  tenant_id        text NOT NULL,
  idempotency_key  text,
  status           text NOT NULL DEFAULT 'queued',  -- queued|running|waiting_input|succeeded|failed|cancelled
  priority         smallint NOT NULL DEFAULT 5,
  input            jsonb NOT NULL,
  progress         jsonb,
  result_ref       text,                            -- object storage key
  error            jsonb,
  attempt          int NOT NULL DEFAULT 0,
  max_attempts     int NOT NULL DEFAULT 3,
  worker_id        text,
  lease_until      timestamptz,                     -- worker must heartbeat before this
  cancel_requested boolean NOT NULL DEFAULT false,
  budget           jsonb,                           -- {max_tokens, max_seconds, max_cost_usd}
  usage            jsonb,
  created_at       timestamptz NOT NULL DEFAULT now(),
  started_at       timestamptz,
  finished_at      timestamptz,
  UNIQUE (tenant_id, idempotency_key)
);
CREATE INDEX runs_claimable ON runs (priority, created_at) WHERE status = 'queued';
CREATE INDEX runs_tenant ON runs (tenant_id, created_at DESC);

CREATE TABLE run_events (                          -- append-only progress log
  run_id  text REFERENCES runs(id),
  seq     bigint,
  at      timestamptz DEFAULT now(),
  kind    text,                                    -- step_started|tool_call|todo_updated|log|...
  data    jsonb,
  PRIMARY KEY (run_id, seq)
);

-- Tenant isolation enforced by the database, not just the app
ALTER TABLE runs ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON runs
  USING (tenant_id = current_setting('app.tenant_id'));

The long-job trap in classic queues. Brokers assume a task takes seconds. If a run takes longer than the broker's redelivery window, the broker assumes the worker died and gives the job to another worker, so two copies of the agent run and you pay twice. Fixes: raise the timeout above your maximum run length, or acknowledge on receipt and track liveness yourself with a lease and heartbeat in Postgres. The second is what the stage-1 design does.

For how the design changes on each specific broker (Kafka, RabbitMQ, Redis, SQS, Azure Storage Queue), see section 8.

Choosing between them

  • Fewer than about 50 runs per minute, small team: Postgres queue. One less moving part, and the queue is transactional with your data.
  • Already running Celery, mostly short jobs: keep it, with acks_late, a raised visibility_timeout, and Postgres-side leases for the long jobs.
  • Many steps, long waits, human approvals, strict retry semantics: Temporal (or Hatchet if you want something Postgres-based and lighter).
  • The agent executes code or browses the web: add per-run sandboxes (Kubernetes Jobs, gVisor, Firecracker-based sandboxes) under whichever orchestrator you pick.

8. The same architecture on Kafka, RabbitMQ, Redis, SQS or Azure Storage Queue

This section swaps the "Queue / engine" box in the reference architecture for a dedicated broker and shows what changes. Some things stay fixed whatever the broker:

  • Postgres stays the source of truth. The run's status, lease, attempt count and result live in the runs table. The broker only carries a pointer: {run_id, tenant_id, trace_context}.
  • The client API doesn't change. Submit, poll, cancel and SSE work the same.
  • Every broker here delivers at least once. Workers must expect duplicates. The conditional claim (UPDATE runs ... WHERE status = 'queued') and the lease turn a duplicate message into a no-op.

What a separate broker adds: the dual-write problem

With the Postgres queue, inserting the run and enqueueing it are one transaction. With a separate broker they're two writes to two systems. If the API crashes between them, you get a run that's never executed, or a message for a run that was never saved. The standard fix is the transactional outbox:

BEGIN;
  INSERT INTO runs (...) VALUES (...);
  INSERT INTO outbox (id, topic, payload) VALUES (gen_random_uuid(), 'runs.pro', '{"run_id": "r_123", ...}');
COMMIT;
-- A relay process (or Debezium reading the Postgres WAL) publishes outbox rows to the broker,
-- then marks them sent. The relay may publish twice; the conditional claim makes that harmless.

A simpler, weaker alternative is to publish after commit and run a periodic "sweeper" that re-publishes runs that have been queued for too long. You need a sweeper anyway to recover expired leases.

Kafka

How the architecture looks: the outbox relay publishes to a runs.requested topic. Workers in one consumer group read it, claim the run in Postgres, and run the agent. Workers also publish progress to a runs.events topic, which feeds SSE, webhooks, analytics and billing.

The problem: Kafka is a log, not a job queue. A consumer owns whole partitions, and its committed offset covers everything before it. With hour-long jobs:

  • One slow run blocks every message behind it in that partition (head-of-line blocking).
  • If processing takes longer than max.poll.interval.ms, the consumer is removed from the group. That triggers a rebalance and redelivery, which means a duplicate run and a stalled group.
  • Parallelism is capped at the partition count. 12 partitions means at most 12 concurrent runs per consumer group, unless each consumer processes many messages at once and tracks offsets itself.

Making it work: treat Kafka as a doorbell. The consumer reads run_id, claims it in Postgres (which gives you the lease), commits the offset straight away, and hands the run to a local pool of async workers. From then on the Postgres lease and the reaper handle crash recovery, not Kafka. At that point Kafka is doing very little that a Postgres queue couldn't. Kafka 4.x adds share groups (KIP-932, "queues for Kafka") with per-message acks; check how mature they are before relying on them.

Where Kafka does fit: the event stream side. Progress events, audit trails, usage metering and fan-out to many consumers (UI, billing, analytics) all benefit from durable, replayable streams.

RabbitMQ

How the architecture looks: the outbox relay publishes to a direct exchange that routes by tier (runs.free, runs.pro, runs.enterprise, all quorum queues). Worker pools consume with prefetch=1 each, so a worker never holds runs it can't start. Failed messages go to a dead-letter exchange.

The long-job decision: pick one of these:

  • Ack at the end. The broker redelivers automatically if the worker dies. But you must raise consumer_timeout above your longest run, and a crash on minute 59 means a full redelivery (cheap if you checkpoint).
  • Ack after claiming in Postgres (recommended). The message only says "go". The Postgres lease and reaper handle crashes, so there's no timeout tuning and no surprise redelivery.

Strengths for this design: real priority queues, routing by tier or tenant, dead-letter exchanges, push delivery with low latency, and it's cloud-agnostic. Per-tenant queues are workable into the low thousands.

Costs: another stateful cluster to run (or a hosted service like CloudAMQP), plus the outbox.

Redis

How the architecture looks: the outbox relay does XADD runs:pro * run_id r_123 to a stream per tier. Workers in a consumer group read with XREADGROUP BLOCK, claim the run in Postgres, and XACK when done. A small reaper calls XAUTOCLAIM for messages that have been pending longer than the lease, and moves messages delivered too many times to a dead stream. (With Lists, the same idea is BLMOVE runs:pro runs:pro:processing, then LREM on completion, and a reaper that returns stale items.) Redis is already in the architecture for rate limits and pub/sub, so this adds no new component.

Strengths: very low latency, blocking reads, cheap per-tenant queues (a key per tenant, with round-robin across them for fairness), sorted sets for delayed retries, and every cloud offers a managed version. Streams also keep history until trimmed, so the same Redis can feed SSE progress events.

Durability is the catch: Redis keeps data in memory. With AOF appendfsync everysec a crash can lose about one second of writes, and replication is asynchronous, so a failover can lose messages the primary had accepted. That's acceptable here only because Postgres is the source of truth: the sweeper re-enqueues any run that stays queued too long, so a lost message means a delay, not a lost run. Don't make Redis the only record of a job.

Long jobs: Streams never redeliver on their own. A message stays pending until someone acks or reclaims it, so there's no 30-minute surprise like RabbitMQ's. The reaper's minimum idle time is your lease, and a worker heartbeats by re-claiming its own message (XCLAIM ... JUSTID). If you use Celery on Redis instead, set visibility_timeout above your longest run, or long runs get executed twice.

AWS SQS

How the architecture looks: one queue per tier, each with a redrive policy to a DLQ (maxReceiveCount = max_attempts). Workers long-poll, claim in Postgres, and extend the message's visibility every few minutes as a heartbeat. They delete the message when the run finishes.

Why it fits well: its visibility-timeout model matches long jobs closely. The heartbeat (ChangeMessageVisibility) is the same thing as the Postgres lease, the DLQ is built in, and there's nothing to operate. Runs longer than 12 hours of total visibility need the ack-early pattern instead.

Multi-tenant options: FIFO queues with MessageGroupId = tenant_id process one run at a time per tenant, which is too strict if tenants are allowed several concurrent runs. Fair queues on standard queues reduce how long quiet tenants wait behind a busy one. Per-tenant concurrency caps still belong in Postgres.

The catch: AWS only. To keep the design portable, hide it behind the Queue interface (enqueue / receive / extend / ack) and use ElasticMQ or LocalStack locally.

Azure Storage Queue

How the architecture looks: the same shape as SQS. A queue per tier, workers poll, call UpdateMessage to extend visibility (each call returns a new pop receipt to use next), and delete the message on completion.

Strengths: very cheap, nothing to operate, and the visibility timeout can be extended up to 7 days.

Gaps you fill yourself: no dead-letter queue (check dequeueCount and move poison messages to a runs-poison queue), no ordering, no long polling (back off when empty), 64 KiB messages, no sessions. Azure Service Bus is Azure's richer option: built-in DLQ, sessions (session ID = tenant ID gives per-tenant ordering), duplicate detection and scheduled messages. Its message locks are short (up to 5 minutes), so long runs need lock renewal or the ack-early pattern.

9. Making a long agent run survivable

Queuing gets the work off the request path. These practices stop an hour of work being lost.

Checkpoint every step

deepagents is built on LangGraph, so you can attach a Postgres checkpointer (langgraph-checkpoint-postgres) and use run_id as the thread_id. After each graph step, the state (messages, todos, virtual files) is saved. If a worker dies, the retry loads the latest checkpoint and continues from step 7, not step 1. This is the biggest cost and latency saving in the whole design.

Leases and heartbeats

The worker holds a lease (lease_until = now() + 60s) and renews it every ~20 seconds from a background task. If the pod is killed, the lease expires and a reaper (or the next claim query) returns the run to queued with attempt + 1. Before writing anything, the worker checks it still holds the lease, so a worker that was paused and came back late can't overwrite the new owner's progress.

Idempotent side effects

A retried step may repeat a tool call. Read-only tools are fine. For tools with side effects (sending email, creating a ticket, charging money), pass an idempotency key derived from run_id + step + call index, or require human approval for that step.

Budgets

Check at each step boundary: maximum wall time, maximum tokens, maximum cost, maximum steps. Deep agents can loop. A hard budget turns a runaway into a failed run with error.code = "budget_exceeded" instead of a large bill.

Cooperative cancellation

Cancel sets a flag (in Postgres, mirrored to Redis so it's cheap to check). The worker checks it between steps and before each LLM call, then stops cleanly and records partial results. Killing a worker mid-step is avoided because it leaves state inconsistent.

Graceful shutdown on deploy

On SIGTERM the worker stops claiming new runs and finishes or checkpoints the current step. Set terminationGracePeriodSeconds to longer than your longest single step, not your longest run. With checkpoints, a run interrupted by a deploy just resumes on a new pod.

Human in the loop

LangGraph's interrupt() saves state and stops. The run moves to waiting_input and holds no worker while it waits, which could be days. POST /resume re-enqueues it with the answer.

Usual approach: pooled by default, bridge for premium or high-volume tenants, silo only when a contract requires it. Keep tenant routing in config so you can move a tenant between models without changing code.

Fair scheduling (the noisy neighbor problem)

With one first-in-first-out queue, a tenant who submits 500 runs makes everyone else wait hours. Options:

TechniqueHowTrade-off
Per-tenant concurrency capAdmission check: running(tenant) < limit(plan). Excess runs stay queued.Simple and essential. Doesn't order runs by itself.
Fair claim queryClaim from the tenant with the fewest running runs (round-robin across tenants), then oldest first within the tenantFair in Postgres with no extra infrastructure. The claim query gets more complex.
Queue per tierruns.free, runs.pro, runs.enterprise with separate worker poolsHard isolation between tiers, but still FIFO within a tier
Queue per tenantA queue for each tenant, workers round-robin across themPerfect fairness, but thousands of queues are hard to operate on most brokers
Engine-native keysHatchet concurrency keys / rate limits, Temporal task queues per tierBuilt in and tested, but tied to that engine

Quotas and cost

  • Submit rate: token bucket per tenant in Redis (e.g. 60 submits per minute).
  • Concurrency: per-plan cap on running runs (above).
  • Spend: monthly token or cost budget per tenant, checked at submit and at each step. Record usage per run for billing.
  • Shared provider limits: your LLM provider's rate limit is shared across all tenants. Divide it with a global limiter in the LLM gateway so one tenant can't use it all.

Data and secrets

  • Tenant ID comes only from the verified token. Set it on the DB session (SET app.tenant_id) so RLS applies even if a query forgets a WHERE clause.
  • The worker re-applies the run's tenant context before doing anything. Tools and retrievers must filter by tenant too (vector store namespaces, search indexes).
  • Object storage keys are prefixed by tenant (tenants/{t}/runs/{id}/report.md). Results are served as presigned URLs valid for a few minutes.
  • Bring-your-own LLM keys: keep them in a secrets manager (Vault, or the cloud's own) and resolve them in the worker at run time. Never store them in the run input.
  • Agent memory and checkpoints are tenant data. Include them in retention and deletion (GDPR erase).

12. Staying cloud-agnostic

The rule is to depend on protocols, not products. Use components that are open source or speak a widely implemented protocol, and treat each cloud's managed version as an interchangeable host.

13. Scaling and observability

Scaling

  • API: standard HPA on CPU or request rate. It's stateless and fast.
  • Workers: KEDA on queue depth or age (it has scalers for PostgreSQL queries, Redis, RabbitMQ, Kafka and NATS). Scaling to zero is possible for low-volume tiers.
  • Concurrency per worker: agent runs mostly wait on LLM and tool I/O, so one async worker can run many at once (e.g. 10 to 50). Cap it by memory, since each run holds its context in RAM.
  • The real bottleneck is usually provider rate limits (tokens per minute), not CPU. Scale workers to your token budget, not to queue depth alone.

Observability

  • Propagate an OpenTelemetry trace context from POST /runs into the job payload, so a single trace covers request, queue wait, and every agent step.
  • Tag every span, log line and Langfuse trace with tenant_id and run_id.
  • Key metrics: queue wait time (p50/p95, per tier), run duration, success, failure and retry rate, lease expiries (crashed workers), cost per run, and per-tenant concurrency against its cap.
  • Alert on oldest queued run age, not queue length. It's the signal users actually feel.
  • Runs that keep failing after max_attempts go to failed with the error kept. That's your dead-letter queue, and it's queryable in SQL.

14. Failure walkthrough

What happensWhat the design does
Client retries the submit after a network blipSame Idempotency-Key, so the unique constraint hits and the API returns the existing run. No duplicate.
API pod dies after inserting but before replyingThe run is committed and queued. The client retries with the same key and gets that run back.
Worker pod is OOM-killed at step 6 of 9The lease expires and the run is reclaimed with attempt=2. It resumes from the step-6 checkpoint.
Deploy rolls all workersOn SIGTERM each worker finishes its step, checkpoints, and releases the lease. New pods resume the runs.
Worker hangs (stuck HTTP call) but the process is alivePer-call timeouts on LLM and tool calls, plus a run-level wall-clock budget. The heartbeat task can also check that progress is advancing.
LLM provider returns 429s or has an outageRetry with backoff in the LLM gateway, fall back to another provider. The run stays running with a progress note rather than failing.
One tenant submits 1,000 runsSubmit rate limit, then the concurrency cap. Excess runs wait in that tenant's share only. Other tenants are unaffected.
Agent loops foreverStep, token or cost budget is exceeded, so the run moves to failed: budget_exceeded with its partial output saved.
Redis is lostRate limits reset briefly and live streams reconnect. No runs are lost because Postgres is the source of truth.
Postgres primary fails overThe API and workers retry their connections. In-flight steps may repeat once, which is safe because of checkpoints and idempotent tools.

15. Recommendation by stage

Stage 1: get it working start here

  • FastAPI API + separate worker deployment, same codebase
  • Postgres: runs + run_events, a SKIP LOCKED claim, leases
  • LangGraph Postgres checkpointer with thread_id = run_id
  • Polling with Retry-After, idempotency keys, RLS
  • Per-tenant concurrency cap, budgets

Infrastructure: Postgres only (plus object storage). Runs on docker-compose locally and on any Kubernetes cluster.

Stage 2: product polish

  • SSE progress stream from run_events
  • Redis for token buckets, cancel flags and pub/sub
  • Signed webhooks with retries
  • Fair claim query across tenants, tier-specific worker pools
  • KEDA autoscaling, OpenTelemetry + Langfuse with tenant tags

Add these when real users need live progress, or when integrations need callbacks.

Stage 3: scale and complexity

  • Move orchestration to Temporal or Hatchet when you need multi-step flows, long waits, approvals and per-step retries
  • Bridge or silo tenants on dedicated pools, or clusters
  • Per-run sandboxes if agents execute code
  • LLM gateway with a global token budget and failover

Add these when hand-built retry and orchestration logic becomes the code you spend the most time maintaining.

The API contract and the runs table stay the same through all three stages. Only what sits behind enqueue() and the worker loop changes, so clients never notice the migration.

A sketch to show the shape, not production code. It leaves out auth, migrations and error handling.

API

from fastapi import FastAPI, Depends, Header, Response, HTTPException
from ulid import ULID

app = FastAPI()

@app.post("/v1/runs", status_code=202)
async def submit_run(body: RunRequest, response: Response,
                     idempotency_key: str = Header(...),
                     tenant: Tenant = Depends(current_tenant),   # from the verified JWT
                     db = Depends(tenant_db)):                    # session with SET app.tenant_id
    await enforce_quotas(tenant)                                  # rate limit + concurrency cap
    run = await db.fetchrow("""
        INSERT INTO runs (id, tenant_id, idempotency_key, input, budget, priority)
        VALUES ($1, $2, $3, $4, $5, $6)
        ON CONFLICT (tenant_id, idempotency_key) DO UPDATE SET idempotency_key = EXCLUDED.idempotency_key
        RETURNING id, status""",
        f"r_{ULID()}", tenant.id, idempotency_key, body.model_dump_json(),
        tenant.plan.budget_json, tenant.plan.priority)
    response.headers["Location"] = f"/v1/runs/{run['id']}"
    return {"id": run["id"], "status": run["status"]}

@app.get("/v1/runs/{run_id}")
async def get_run(run_id: str, response: Response, db = Depends(tenant_db)):
    run = await db.fetchrow("SELECT * FROM runs WHERE id = $1", run_id)  # RLS hides other tenants
    if not run:
        raise HTTPException(404)
    if run["status"] in ("queued", "running"):
        response.headers["Retry-After"] = "5"
    return to_public(run)   # includes a presigned result_url when succeeded

Worker

CLAIM_SQL = """
UPDATE runs SET status = 'running', worker_id = $1, attempt = attempt + 1,
                lease_until = now() + interval '60 seconds',
                started_at = coalesce(started_at, now())
WHERE id = (
  SELECT id FROM runs
  WHERE (status = 'queued' OR (status = 'running' AND lease_until < now()))
    AND attempt < max_attempts
    AND NOT cancel_requested
  ORDER BY priority, created_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1)
RETURNING *;
"""

async def worker_loop(worker_id: str):
    while not shutting_down.is_set():
        run = await db.fetchrow(CLAIM_SQL, worker_id)
        if not run:
            await asyncio.sleep(1)          # or wait on LISTEN/NOTIFY
            continue
        heartbeat = asyncio.create_task(renew_lease_every(20, run["id"], worker_id))
        try:
            await execute_agent(run)
        finally:
            heartbeat.cancel()

async def execute_agent(run):
    agent = create_deep_agent(..., checkpointer=postgres_checkpointer)  # resumes if a checkpoint exists
    config = {"configurable": {"thread_id": run["id"], "tenant_id": run["tenant_id"]},
              "callbacks": [langfuse_handler(run)]}
    async for step in agent.astream(initial_input_or_none(run), config, stream_mode="updates"):
        await append_event(run, step)                  # run_events + Redis publish
        if await cancel_requested(run["id"]):
            return await finish(run, "cancelled")
        if over_budget(run, step):
            return await finish(run, "failed", error="budget_exceeded")
    report = await agent.aget_state(config)
    key = await put_object(f"tenants/{run['tenant_id']}/runs/{run['id']}/report.md", report)
    await finish(run, "succeeded", result_ref=key)     # UPDATE ... WHERE worker_id = $me (fencing)

Two details matter here. First, finish() only updates if this worker still owns the run, which stops a stale worker from overwriting a newer attempt. Second, when a checkpoint exists, initial_input_or_none returns None, so LangGraph continues from the saved state instead of starting again.

Moving to Temporal later

The same flow becomes a workflow: submit calls client.start_workflow(id=run_id), each agent step or subagent becomes an activity that sends heartbeats, cancellation becomes a workflow cancel, and human approval becomes a signal. The runs table stays as the tenant-facing view and is updated from the workflow.
