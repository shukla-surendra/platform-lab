# Architecture Discussion

Open-ended design write-ups: one problem, the options, and their trade-offs. Unlike the numbered
case studies in this section, these come from real backend questions rather than interview prompts.

| Topic | What it covers |
|---|---|
| [Long-running agent jobs in a multi-tenant system](long_running_agent_jobs.html) | Moving a FastAPI agent endpoint to submit-and-poll background runs: async request-reply, execution options (Postgres queue, Celery, Kafka, Temporal/Hatchet, K8s Jobs), the same design on Kafka vs RabbitMQ vs Redis vs SQS vs Azure Storage Queue, checkpointing and leases, polling vs SSE vs webhooks, tenant isolation and fairness, cloud-agnostic component mapping |
| [Messaging tools compared](messaging_tools_compared.html) | What Redis, RabbitMQ, Kafka, NATS, Pulsar, Postgres-as-queue, workflow engines and the cloud queues (SQS, SNS, Pub/Sub, Service Bus, Storage Queue, Event Hubs, Kinesis) are; queue vs pub/sub vs log vs workflow; why Kafka is a log, not a job queue; comparison table, when-to-use guide, common mistakes |
| [Kafka field guide](kafka_field_guide.html) | Why Kafka exists and the problem it solves, the mental model on one page, ten practical use cases (microservices, CDC, pipelines, logs, clickstreams, stream processing, event sourcing, ML features, IoT, data sharing), when not to use it, and an experienced engineer's notebook: topic/key/schema design, producer and consumer settings, outbox, idempotency, retries and DLTs, exactly-once limits, cluster operations, monitoring, common incidents, ecosystem; plus a design review checklist, key numbers and a hands-on path to expertise |
| [RabbitMQ field guide](rabbitmq_field_guide.html) | Same shape as the Kafka guide: why a message broker, the exchange/queue model, use cases (job queues, commands, pub/sub, routing, load levelling, RPC, delays, MQTT, streams), when not to use it, and the notebook: exchange and queue design, publisher confirms, prefetch and acks, consumer timeouts and heartbeats, retries with TTL queues and DLX, classic vs quorum vs stream queues, cluster operations and alarms, monitoring, common incidents, ecosystem |
| [Redis field guide](redis_field_guide.html) | Same shape: why an in-memory data structure server, the data types, use cases (caching, sessions, rate limits, counters, leaderboards, queues, locks, pub/sub, dedup, geo/vectors), when not to use it, and the notebook: key design, big and hot keys, cache-aside and stampedes, maxmemory and eviction, the single thread, persistence and fork, Sentinel and Cluster, streams vs pub/sub, locks and fencing, clients, security, monitoring, common incidents, licences and Valkey |
| [Postgres as a queue](postgres_as_a_queue.html) | How a queue is built from a table + `FOR UPDATE SKIP LOCKED`: claim query, leases and heartbeats, crash recovery, retries with backoff, why 50 pods never claim the same job (tested, with fencing tokens and idempotency), LISTEN/NOTIFY, measured cost of polling (with a benchmark script), a runnable Python worker, pgmq and libraries, limits and when to move on |
| [Postgres job queue: load, sizing and per-tenant limits](postgres_queue_case_study.html) | Case study of the lab's job management app: measured cost per job, heartbeat and worker (WAL, commits, HOT updates), where the load really comes from (connections and heartbeats, not jobs), sizing formulas with an interactive calculator, instance recommendations for 10, 100 and 1,000 jobs/s, a tested per-tenant concurrency cap + token-bucket rate limit + backlog quota + fair ordering in plain SQL, tuning steps, what to monitor, sharing one Postgres with the app (risks, guard rails, how to separate step by step), the thresholds for moving to a message broker, AWS cost comparison (shared vs dedicated Postgres vs SQS vs RabbitMQ), and where brokers store messages and why job state still needs a database |

[`postgres_queue_lab/`](postgres_queue_lab/) holds the runnable scripts behind the Postgres page's concurrency tests, and the job management app (web UI + workers in Docker) that the case study measures.

[`rabbitmq_kafka_lab/`](rabbitmq_kafka_lab/) is a hands-on Docker Compose lab: six small lessons showing how RabbitMQ (a queue) and Kafka (a log) behave differently.

Open the `.html` files directly in a browser.
