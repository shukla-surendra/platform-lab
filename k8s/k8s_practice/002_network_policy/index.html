Kubernetes NetworkPolicy examples

Seven independent examples. Each folder is complete on its own: its own namespaces, app, policy, test script, README and page. Run any one, in any order.

01
Deny all incoming traffic
One policy with an empty pod selector blocks every incoming connection to every pod in a namespace.
02
Allow traffic from one pod only
A policy can let in traffic only from pods with a certain label, and block every other pod.
03
Allow one port only
A policy can open one port on a pod and keep its other ports closed.
04
Allow traffic from another namespace
A policy can let in traffic from a whole namespace, selected by its labels.
05
AND vs OR selectors
One extra "-" in the YAML turns a narrow rule (AND) into a much wider one (OR).
06
Deny outgoing traffic, then allow DNS
Blocking outgoing traffic also blocks DNS lookups, so egress lockdowns almost always need a DNS rule.
07
Lock down a three-tier app
Combining deny-all, DNS, and per-tier allow rules leaves only the app's intended paths open.

Every example runs the same way

cd 01_deny_all_ingress
./demo.sh           # create the app, test, apply the policy, test again
./demo.sh cleanup   # delete what this example created

What a NetworkPolicy is

By default every pod can connect to every other pod. A NetworkPolicy is a firewall rule for pods: it picks pods by label and says which connections may come in (ingress) or go out (egress).

  1. A pod that no policy selects allows everything.
  2. Once a policy selects a pod for ingress (or egress), that direction is deny by default for the pod.
  3. Policies only allow. Several policies on one pod add up.
  4. A connection needs egress allowed on the sender and ingress allowed on the receiver.
  5. Replies to an allowed connection are allowed automatically.

Troubleshooting

If a result says ✗ unexpected even after 90 seconds, the network plugin may have stopped applying changes. On this cluster, restarting kindnet fixed it: kubectl -n kube-system delete pod -l app=kindnet, then run ./demo.sh again.
