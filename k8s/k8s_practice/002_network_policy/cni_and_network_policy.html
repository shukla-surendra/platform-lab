Every folder has the same files

FileWhat it is
app.yamlThe example's namespaces, pods and services. Web servers are nginx:1.27-alpine, the database is redis:7-alpine, clients are busybox:1.36 (it has nc and nslookup for testing).
policy.yamlThe NetworkPolicy. Examples 05 and 06 have two policy files, applied one after the other.

How demo.sh tests a connection

# TCP: open a connection from a pod to a Service and close it straight away (-z), give up after 2 s (-w 2)
kubectl -n np-02 exec stranger -- nc -z -w 2 api 80 && echo ok || echo BLOCKED

# DNS: look up a name from inside a pod
kubectl -n np-06 exec client -- nslookup -timeout=2 web.np-06.svc.cluster.local

A blocked connection doesn't get an error back. The packets are dropped, so the connection just times out. Policy changes can take a few seconds to reach every node, so demo.sh retries for up to 90 seconds before reporting a mismatch.

Verified on this cluster

All seven examples were run on the local minikube cluster (Kubernetes v1.34.0, 2 nodes, kindnet). Every check matched its expected result.

Issue found while testing: kindnet stopped applying policy changes partway through. Example 01's deny-all policy existed but traffic still flowed for several minutes. Restarting the kindnet pods fixed it (they're a DaemonSet, so Kubernetes recreates them immediately):

kubectl -n kube-system delete pod -l app=kindnet

If a demo.sh result shows ✗ unexpected after 90 seconds, do this, then run the example again.

2. What a CNI plugin is, and why it matters for NetworkPolicy

CNI (Container Network Interface) is the standard Kubernetes uses to plug pods into the network. Kubernetes itself doesn't do pod networking: when a pod starts, the kubelet asks the CNI plugin to give it a network interface and an IP address, and the plugin makes sure pods on different nodes can reach each other.

Kubernetes also doesn't enforce NetworkPolicy itself. The API server just stores the policy objects. An agent from the CNI plugin, running on every node, watches those policies and turns them into packet-filtering rules (iptables, nftables or eBPF) on that node.

The silent failure: on a cluster whose CNI doesn't support NetworkPolicy, Kubernetes accepts the YAML, kubectl get netpol lists it, and nothing is blocked. There's no error or warning. Always test (section 5).

3. Which CNI plugins support NetworkPolicy

Support changes between versions. Check the plugin's own docs for the version you run, and test it.

CNI pluginEnforces NetworkPolicy?Notes
CalicoYesThe most widely used policy engine. Adds its own NetworkPolicy and cluster-wide GlobalNetworkPolicy with explicit deny rules, ordering and logging. Can also run in "policy-only" mode on top of another CNI.
CiliumYeseBPF-based. Adds CiliumNetworkPolicy and CiliumClusterwideNetworkPolicy with layer 7 rules (HTTP paths, DNS names). Hubble shows which flows were allowed or dropped.
AntreaYesOpen vSwitch-based. Adds tiered, cluster-wide policies.
kube-routerYesLightweight. k3s uses its policy controller to enforce NetworkPolicy alongside Flannel.
CanalYesFlannel for networking plus Calico for policy.
OVN-Kubernetes, Kube-OVNYesOVN-based. OVN-Kubernetes is the default in OpenShift.
kindnetYes, in recent versionsThe simple CNI from kind. Newer releases added NetworkPolicy support (older ones had none). This cluster runs kindnet and enforces policies, though it needed a restart once (section 1).
FlannelNoNetworking only. Pair it with Calico (Canal) or another policy engine.

4. How to check which CNI you have

Method 1: look at the pods in kube-system (works everywhere)

Every CNI runs an agent on each node, usually a DaemonSet. Its pod names give it away.

$ kubectl get pods -n kube-system -o wide | grep -iE "kindnet|calico|cilium|flannel|weave|antrea|aws-node"
kindnet-bwbhx   1/1   Running   minikube-m03
kindnet-gjh4x   1/1   Running   minikube

$ kubectl get daemonsets -n kube-system
NAME         DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR            AGE
kindnet      2         2         2       2            2           <none>                   6d20h
kube-proxy   2         2         2       2            2           kubernetes.io/os=linux   6d20h

Real output from this cluster: one kindnet pod per node. Some CNIs install into their own namespace instead, so check those too:

kubectl get ns | grep -iE "calico|tigera|cilium|flannel|antrea"
kubectl get pods -A | grep -iE "calico|cilium|flannel|antrea|weave|kube-router|aws-node|azure-cns"
You see pods named…Your CNI is
kindnet-*kindnet
calico-node-*, calico-kube-controllers-*, namespace calico-system / tigera-operatorCalico
cilium-*, cilium-operator-*Cilium
kube-flannel-ds-* (namespace kube-flannel)Flannel (no policy support on its own)
canal-*Canal (Flannel + Calico)
antrea-agent-*Antrea
aws-node-*Amazon VPC CNI
azure-cns-*, azure-npm-*Azure CNI (NPM = Azure's policy manager)
Nothing network-related at allProbably the basic bridge plugin: check method 2

Method 2: read the CNI config on a node

The kubelet uses the first config file (alphabetically) in /etc/cni/net.d/.

$ minikube ssh -- ls /etc/cni/net.d/
10-kindnet.conflist
200-loopback.conf
100-crio-bridge.conf.mk_disabled
87-podman-bridge.conflist.mk_disabled

$ minikube ssh -- sudo cat /etc/cni/net.d/10-kindnet.conflist
{
  "cniVersion": "0.3.1",
  "name": "kindnet",
  "plugins": [ { "type": "ptp", ... }, { "type": "portmap", ... } ]
}

Here 10-kindnet.conflist is active. minikube renamed the other configs to .mk_disabled so they're ignored. On a regular node, run ls /etc/cni/net.d/ over SSH, or start a debug pod with kubectl debug node/<node> -it --image=busybox and look under /host/etc/cni/net.d/.

Method 3: ask your tool or cloud

# minikube: the CNI setting of each profile (empty = minikube chose automatically)
minikube profile list -o json

# AWS EKS
aws eks describe-addon --cluster-name <cluster> --addon-name vpc-cni

# Azure AKS
az aks show -g <resource-group> -n <cluster> --query networkProfile

# Google GKE: ADVANCED_DATAPATH means Dataplane V2
gcloud container clusters describe <cluster> --format="value(networkConfig.datapathProvider)"

Method 4: the CNI's image version

$ kubectl -n kube-system get ds kindnet -o jsonpath='{.spec.template.spec.containers[0].image}'
docker.io/kindest/kindnetd:v20250512-df8de77b

The version tells you which features to expect. For example, older kindnet versions have no policy support.

5. How to test that policies are really enforced

Knowing the CNI's name isn't enough: versions differ, and a feature can be switched off. This 30-second test gives a definite answer:

kubectl create namespace np-test
kubectl -n np-test run web --image=nginx:1.27-alpine --labels=app=web --port=80 --expose
kubectl -n np-test run client --image=busybox:1.36 -- sleep infinity
kubectl -n np-test wait --for=condition=Ready pod --all

kubectl -n np-test exec client -- nc -z -w 2 web 80 && echo ok || echo BLOCKED   # expect: ok

kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: deny-all, namespace: np-test}
spec: {podSelector: {}, policyTypes: [Ingress]}
EOF
sleep 15
kubectl -n np-test exec client -- nc -z -w 2 web 80 && echo ok || echo BLOCKED   # BLOCKED = enforced

kubectl delete namespace np-test

If the second test still says ok after a minute, your CNI isn't enforcing policies. Example 01 runs the same test with automatic checks.

6. How to disable a CNI and enable a new one

Read this first: a cluster runs one primary CNI. Every pod's IP address and network interface comes from it. Swapping it on a running cluster disconnects every pod until it's recreated on the new network. For learning, create a new cluster with the CNI you want. In production, follow the vendor's migration guide or move workloads to a new cluster or node pool.

Two kinds of change

ChangeDisruptionExamples
Add policy enforcement to the CNI you already haveLow: networking stays the same, a policy agent is addedCalico in policy-only mode on top of Flannel (Canal), Cilium in chaining mode, turning on the EKS VPC CNI network policy feature, choosing a network policy engine on AKS
Replace the CNI itselfHigh: every pod gets a new networkFlannel → Calico, kindnet → Cilium, kubenet → Azure CNI

minikube

Pick the CNI when you create the cluster, with --cni. You can't safely change it on an existing profile, so use a new profile. Your current minikube profile stays untouched.

minikube start -p calico-lab --cni=calico           # built-in options: auto, bridge, calico, cilium, flannel, kindnet
minikube start -p cilium-lab --cni=cilium
minikube start -p byo-cni --cni=false               # no CNI: install your own (pods stay Pending until you do)
minikube start -p byo-cni --cni=/path/to/cni.yaml   # or apply your own CNI manifest

kubectl config use-context calico-lab               # switch kubectl between clusters
minikube delete -p calico-lab                       # remove the extra cluster when done

kind

# kind-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
networking:
  disableDefaultCNI: true        # don't install kindnet
  podSubnet: 192.168.0.0/16      # match what the CNI you install expects

kind create cluster --config kind-config.yaml
# nodes stay NotReady until you install a CNI, for example Calico or Cilium (below)

kubeadm (self-managed clusters)

  1. kubeadm init --pod-network-cidr=<cidr>. kubeadm installs no CNI, and nodes stay NotReady until you add one.
  2. Install the CNI (manifest, Helm chart, or operator). Its pod CIDR must match the one from step 1.
  3. To remove a CNI: delete its DaemonSet, operator and CRDs, remove its files from /etc/cni/net.d/ on every node, clean up its leftover interfaces and rules (rebooting the nodes is the simplest way), then install the new CNI and restart every pod.

k3s

# start k3s without Flannel and without the built-in policy controller, then install your own CNI
curl -sfL https://get.k3s.io | INSTALL_K3S_EXEC="--flannel-backend=none --disable-network-policy" sh -

Installing Calico or Cilium

Use the install page for the exact version you want: the commands change between releases.

# Calico: the operator, then a resource describing the install (URLs are on docs.tigera.io)
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/<version>/manifests/tigera-operator.yaml
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/<version>/manifests/custom-resources.yaml
kubectl get pods -n calico-system --watch           # wait for calico-node to be Running on every node

# Cilium: with the cilium CLI ...
cilium install
cilium status --wait
# ... or with Helm
helm repo add cilium https://helm.cilium.io/
helm install cilium cilium/cilium --namespace kube-system

7. Try it: a second minikube cluster with Calico or Cilium

All seven examples are independent and only use standard NetworkPolicy, so they should work on any CNI that enforces policies. To compare CNIs without touching your current cluster:

minikube start -p calico-lab --cni=calico --nodes=2
kubectl config use-context calico-lab
kubectl get pods -n kube-system | grep calico      # method 1 should now show calico-node pods

cd k8s/k8s_practice/002_network_policy/02_allow_from_one_pod
./demo.sh                                           # should give the same results as on kindnet
./demo.sh cleanup

kubectl config use-context minikube                 # back to the original cluster
minikube delete -p calico-lab                       # remove the test cluster

Each extra minikube cluster uses a few GB of memory. Stop other heavy containers first if your machine is short on RAM.
