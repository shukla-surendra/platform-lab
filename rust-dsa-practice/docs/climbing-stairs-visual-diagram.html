ways(n) counts finished paths — not extra steps

The feeling that we’re “missing a step” from n−1 to n and from n−2 to n is correct — that hop really happens. It just isn’t happening to the two numbers being added. It happens inside each path, before the addition ever runs.

First, trace it as the actual function calls

This is exactly what ways(4) does when you run it — nothing simplified, nothing skipped. Amber edges are the n−1 branch, teal edges are the n−2 branch, and dashed boxes are base cases — they return 1 immediately and split no further.

Now trace the same thing as real paths

ways(n−1) isn’t a distance. It’s a completed set: every distinct sequence of 1s and 2s that already sums to n−1. Take ways(3) for n = 4 — that’s the three finished climbs 1+1+1, 1+2, 2+1, each one already standing on step 3.

Tack one more +1 onto the end of all three, and every one of them now lands on step 4. You didn’t create or delete a path — you relabelled where three existing paths end. The count stays 3.

Reading the equation again

A path to step 4 has exactly one last move, and it’s either a 1 or a 2 — never both, never neither. So the five paths split into two groups that share nothing. Group sizes that share nothing just add: 5 = 3 + 2.

The +1 and +2 hops you’re looking for aren’t missing from the formula — they’re the reason a path belongs to one group instead of the other. They already did their work before ways(n−1) + ways(n−2) ever gets evaluated.

A bigger example: n = 5

Same everything, one size up. ways(5) = 8. Here’s the full recursion tree — it’s just the n = 4 tree with one more layer of “ask two smaller questions” wrapped around it.

The same tree, but watched as it actually runs

A tree diagram shows the finished shape. What the computer actually does is a single sequence of events over time — and because ways(n−1) is written before ways(n−2) in the code, it runs its entire left branch, all the way down and back up, before it even starts on the right one. That’s why this is called a stack: each call gets pushed on top, and only pops back off once it has its answer.

call ways(5)
call ways(4)
call ways(3)
call ways(2)
ways(1) = 1 [base]
ways(0) = 1 [base]
return ways(2) = 1 + 1 = 2
ways(1) = 1 [base]
return ways(3) = 2 + 1 = 3
call ways(2)
ways(1) = 1 [base]
ways(0) = 1 [base]
return ways(2) = 1 + 1 = 2
return ways(4) = 3 + 2 = 5
call ways(3)
call ways(2)
ways(1) = 1 [base]
ways(0) = 1 [base]
return ways(2) = 1 + 1 = 2
ways(1) = 1 [base]
return ways(3) = 2 + 1 = 3
return ways(5) = 5 + 3 = 8

Indentation = how deep the stack is at that moment. Every single addition in this whole trace — 1+1, 2+1, 1+1 again, 3+2 — is two numbers that already finished being computed. None of them is a step being tacked on; the step-taking already happened, silently, in the shape of the tree itself.

And the paths themselves, for n = 5

Grouped by last hop, exactly like before. Look closely at the part before the bold last hop in each group — those are precisely the 5 paths and 3 paths from the n = 4 figure and the n = 3 example at the very top of this file. Nothing new is being invented at n = 5; it’s the same two finished sets, each with one more hop glued on.

ways(n) for n = 0 to 15

No tree fits past n = 5 without turning into a wall of boxes, but the recurrence doesn’t care — it keeps working the same way forever. Each row is still just the two rows above it, added: 610 = 377 + 233, 987 = 610 + 377. It’s the Fibonacci sequence, one position over.
